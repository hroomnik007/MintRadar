# /methodology and /for-wallets — the two public reference pages (2026-10-13)

Two static pages, lazy routes in `routerLazy.tsx` / `App.tsx`, linked from the footer ("Methodology", "For wallets") but NOT from the main navigation. Both use the About page shell (`About.css`: `.about-page`, `.about-toc`, `.about-text`, `.about-note`, `.about-card`) plus `DocPage.css` (h3/h4, `.doc-table-wrap`, the change log, `.doc-code`); the scroll helpers are `hooks/useDocPageScroll.ts` (the same behaviour as the private ones in `About.tsx`, which is unchanged). Each sets title, description, canonical and og:* through `useDocumentMeta` (og:image stays the generic one); **the title and description are `PAGE_META['/methodology']` / `PAGE_META['/for-wallets']` (`src/utils/pageMeta.ts`, shared with the backend bot HTML `GET /api/og/page` — change the text only there, see "Bot HTML for /methodology and /for-wallets" in `deploy-and-infra.md`)**. Neither page fetches anything: no API call, no third-party host (e2e records every request and WebSocket and expects only the app's own host).

## /methodology — `pages/Methodology.tsx`

The canonical, versioned description of the Reliability Score. **Every number on the page comes from `METHODOLOGY_PAGE` (`src/constants/methodologyPage.ts`); the change log is rendered from `METHODOLOGY_CHANGES` (`src/utils/methodology.ts`, newest first).** `src/__tests__/methodologyPage.test.tsx` compares each value with the code that computes the score: component maxima (via `uptimeComponent`, `auditComponent`, `nutComponent`, `versionComponent`, `contactComponent`), the audit bands and their edges, neutral value, minimum swaps, freshness hours, the tracked NUT list, the version threshold and points table, the 14-day release grace period (`VERSION_GRACE_PERIOD_MS`), the cap and its days, the 14-day recommendation gate, the cadences (`cron.ts`, `PROBE_TIMEOUT_MS`, the 24 h window in `prober.ts`, the 60 s snapshot). The contact card repeats `About.tsx` (`constants/contact.ts`; a test fails when About stops containing the same npub, NIP-05 and repository). Content rules: operational health signal, never solvency or a recommendation; reviews (Community Rating) are separate and never part of the score; since 2026-10-13 one short section "Where the score is published" (`#where-published`) points to the API for wallets and to the signed health assertions (`/for-wallets#signed-health-assertions`; rank = the score, `methodology` = the number on the page). Adding it needed no `METHODOLOGY_CHANGES` entry (the formula did not change).

**Rule: any change to the formula (weights, the audit rule, the version rule, the new-mint cap, the recommendation gate) adds a `METHODOLOGY_CHANGES` entry and bumps `METHODOLOGY_VERSION` in the SAME commit — in `backend/src/shared/methodology.ts` AND the byte-identical frontend copy `src/utils/methodology.ts` (`sharedModules.test.ts` fails when they drift) — and updates `methodologyPage.ts` and the prose of `Methodology.tsx`. The test fails when a constant changes without the page.** The same entry also goes into the table in `docs/API.md` ("Stability").

## /for-wallets — `pages/ForWallets.tsx`

Quick start for the Wallet API v1 (contract: `docs/API.md` "API for wallets (v1)", `docs/openapi/wallets-v1.yaml`). The field, parameter, envelope and error tables are rendered from `WALLET_MINT_FIELDS`, `WALLET_ENVELOPE_FIELDS`, `WALLET_QUERY_PARAMS` and `WALLET_ERRORS` (`backend/src/shared/walletFields.ts`, re-exported from `walletApi.ts`; frontend copy `src/utils/walletFields.ts`, byte-identical, checked in `sharedModules.test.ts`). The code examples and the quoted numbers (poll interval, 300/min, 90-day notice) are in `constants/forWalletsPage.ts`. `src/__tests__/forWalletsPage.test.tsx` compares the lists with the REAL mapper (`toWalletMint`: keys, nested keys, nullability, types), the envelopes, `parseWalletListQuery` (every documented parameter is read; defaults and the limit range), the `sendWalletError` codes in `index.ts`, `sendCachedBody` (Cache-Control, ETag), and checks that every example URL uses only documented parameters, the only request header is `If-None-Match`, and the response fields they read exist.

**Rule: a new field in `WalletMint` needs its line in `WALLET_MINT_FIELDS` (both copies) in the same commit; the test fails otherwise.** Since 2026-10-20 (W2b) nested names are listed as `parent.child` one level deep (`authRequired.clear`, `sample.probes24h`, `methods.mint`, `scoreBreakdown.sum`, ...), the single-mint-only `canonicalUrl` is an ENVELOPE field, and the OpenAPI test treats `pubkey`, `firstSeenAt`, `lastOnlineAt`, `sample`, `keysets`, `keysetsCheckedAt`, `methods` and `scoreBreakdown` as optional (only with `include=` / on the single-mint endpoint). The page shows a "Privacy of your request" paragraph (`data-testid="request-privacy"`) and the 2026-10-20 additions list (`data-testid="additions"`; date `WALLET_API_FACTS.walletAdditionsOn`). Inside v1 fields are never renamed or removed. The example mint URL is a real, tracked mint (`https://mint.minibits.cash/Bitcoin`; check that `GET /api/v1/wallets/mints/<encoded url>` still answers 200 if the example is ever suspected stale).

`CodeBlock` (`components/CodeBlock.tsx`): the code scrolls sideways INSIDE the `<pre tabindex=0>` (never the page), the copy button follows the account menu's clipboard pattern ("Copied" / "Copy failed", plus a `role=status` live region).

## Rule: wallet-facing documents follow the code (2026-10-17)

`docs/API.md` ("API for wallets (v1)" and the sections below it), `docs/openapi/wallets-v1.yaml`, `docs/nostr-health-assertions.md`, the `/for-wallets` page and `src/utils/walletFields.ts` (with its byte-identical backend copy `backend/src/shared/walletFields.ts`) say what the CODE does, never the other way round. When an endpoint, a field, a parameter, an error, a limit or a cache header changes, update API.md, the OpenAPI file and `walletFields.ts` together in the same commit. `src/__tests__/walletDocsConsistency.test.ts` enforces the constants: mint, envelope, parameter (with defaults) and error names of the OpenAPI file and of the API.md tables against `WALLET_*`, the rate-limit number against `WALLET_API_FACTS` and `backend/src/index.ts`, and the methodology version table against `METHODOLOGY_CHANGES`/`METHODOLOGY_VERSION`; a failure names the file and the name that differ. What the test cannot see (prose such as the `status` rules, cache lifetimes of internal routes, the 90-day notice) is checked by hand against the code at each release of the API.

Facts established in the 2026-10-17 accuracy pass (code is the source): `status` — `degraded` = latest probe failed and (at least 4 probes in the last 24 h all failed, or that failed probe is older than 24 h), `archived` = latest probe failed and the last success is older than 30 days (checked first; a never-successful mint is not archived) — `backend/src/degraded.ts` + `index.ts` (`computeKnownMints`) + `walletApi.ts` (`statusOf`). The wallet routes and `/api/mints/recommend` share ONE counter, 300/min/IP (`index.ts` `WALLET_RATE_LIMIT_MAX`, `usesWalletRateLimit`). ETags are strong in the backend but reach gzip-capable clients as `W/"…"` (nginx). **Since 2026-10-20 exactly one route sends `Deprecation`/`Sunset`/`Link: rel=successor-version` headers: `/api/v1/mints/recommend` and its unversioned alias** (`backend/src/deprecation.ts`, the one constant `RECOMMEND_DEPRECATION`; `deprecation.test.ts` fails when Sunset is less than 90 days after the Deprecation date). The page, API.md and the OpenAPI file quote the same dates (`WALLET_API_FACTS.recommendDeprecatedOn/SunsetOn`, compared with the backend constant in `forWalletsPage.test.tsx`); to deprecate another route reuse `setDeprecationHeaders`, then update those three documents. The 90-day notice (`WALLET_API_FACTS.deprecationNoticeDays`) is the promise. The list parameters `nuts` and `eligible` were added the same day (WALLET_QUERY_PARAMS, both walletFields copies, API.md table, OpenAPI parameters; `eligible=false` keeps only the ineligible mints). `/api/stats/reliability-trend` sends `public, max-age=600`.
