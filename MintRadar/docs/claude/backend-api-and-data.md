### mint_reviews (added 2026-08-30 — review-load perf work)
```
url TEXT REFERENCES mints(url) ON DELETE CASCADE
pubkey TEXT NOT NULL
event_id TEXT NOT NULL
rating INTEGER            -- null for rating-less endorsement events
comment TEXT NOT NULL DEFAULT ''   -- capped at 2000 chars on write
created_at BIGINT NOT NULL         -- nostr event created_at (unix seconds)
PRIMARY KEY (url, pubkey)          -- one row per author per mint, newest wins
```
Index: (url, created_at DESC). Populated by the hourly reviews sync (`backend/src/reviewsSync.ts`).
`reviews_sync_relay_state` (relay TEXT PK, `last_ok_started_at` BIGINT NULL (NULL = counters row of a relay that never finished a clean run; ignored by the sync), `last_full_at` BIGINT NULL; unix seconds) — per-relay progress of that sync: when the last clean run on the relay started and when the last full sweep did. Drives the `since` of the next incremental query. Since 2026-10-13 the same row also holds per-relay delivery counters (`runs`, `ok_runs`, `failed_runs`, `skipped_runs`, `events_delivered`, `events_exclusive`, `events_new`, `total_ms`, `last_run_exclusive`, `counters_since`; counts only, see "Relay delivery counters" in `docs/claude/reviews-and-nostr.md`); see "Reviews sync" in `docs/claude/reviews-and-nostr.md`.
Rollup columns on `mints`: `review_count INTEGER`, `review_avg_rating REAL`, `reviews_checked_at TIMESTAMPTZ`.
`review_count_7d_ago INTEGER` + `review_count_7d_ago_at TIMESTAMPTZ` — rolling ~1-week-ago `review_count` snapshot, advanced once a day (`reviewSurgeRollup.ts`); feeds the informational "recent review surge" sybil flag (see Reviews Feature below).

### audit_cz_mints / audit_cz_aliases / audit_cz_swaps (added 2026-10-04 — cashu.info, formerly audit.cashu.cz, display only; the table names, the `source` value and the endpoint path keep the historical name on purpose)
Second, public audit source (`backend/src/auditCz.ts`). **These three tables stay display only**: the prober and `/api/mints/known` never read them. Since 2026-10-08 two numbers of the per-mint detail reach the Reliability Score, but through `mints.audit_cz_*` (see `audit_cz_detail` below), never from these tables at probe time. No FK to `mints`; no row is ever created in `mints` from this source.
```
audit_cz_mints(url PK [normalised], state ok|warn|error, uptime24h, uptime7d, uptime30d DOUBLE, attributed_failures INT, minted INT, melted INT [their list feed's counts, nullable],
               last_check TIMESTAMPTZ, page TEXT [https://cashu.info/mint/<id>, BUILT by `auditCzPageUrl(id)` from the feed id after `^[A-Za-z0-9]{8,64}$`; never the feed's own `page`; a boot migration in `db.ts` rewrites rows that still hold https://audit.cashu.cz/mint/<id> (idempotent)], fetched_at, source='audit.cashu.cz')
audit_cz_aliases(alias_url PK, mint_url, fetched_at)      -- their aliases[], normalised
audit_cz_swaps(id TEXT PK, at, status short lowercase token (success, failed, pending, or any other `^[a-z][a-z_-]{0,29}$` token the source sends), stage short lowercase token (melt, mint, balance, limits, …) or NULL, error ≤300 chars,
               amount, fee, duration_ms, from_url, to_url, from_name, to_name, fetched_at, source)
  indexes: (from_url, at DESC), (to_url, at DESC), (at DESC)
```
Keys use `normalizeUrl()` plus a stripped trailing slash (`auditCzKey`); a tracked mint matches when its key equals their `url` or any alias (our DB has no alias data of its own — `aliasOf` is only a submit/discover hint). Swaps are stored as given and matched at read time (from or to) through the same url+aliases set. Sync: upserts, one transaction per response; any failure (timeout, HTTP error, >1 MiB, bad JSON, bad top-level shape) writes and deletes nothing; malformed items are skipped; pruning (>14 days, hard cap 20000 rows) only after a successful swaps write.

### audit_cz_detail (added 2026-10-07 — cashu.info per-mint detail; display, plus two numbers copied to `mints.audit_cz_*` for the Reliability Score since 2026-10-08)
```
audit_cz_detail(url TEXT PK [= audit_cz_mints.url], detail JSONB [validated subset only: swaps7d {all/asSource/asDest {total,success,failed,avgMs}, errorsBlamed, dleq}, integrity {proof_state {checked,spent,pending}}, network {asn, asName, country}, onion (boolean); pruned 2026-10-07: step timings, swap_test, TLS, ipv4/ipv6 flags, latency], fetched_at)
```
Never stored: score, scoreParts, reviews, daily, changes, incidents7d, Frankfurt data, spec details (the onion address becomes a boolean). The only IP kept anywhere is the mint host's own public IPv4, resolved by us into `mints.ip_address` (`mintAddress.ts`, boot + every 6 h), never the source's data. Written only by `syncAuditCzDetails()` (`backend/src/auditCzDetail.ts`); a failed fetch writes and deletes nothing. The same statement (a CTE: upsert + `UPDATE mints`) copies `swaps7d.all.total`, `swaps7d.errorsBlamed` and the fetch time to `mints.audit_cz_total` / `audit_cz_blamed` / `audit_cz_fetched_at` of every tracked mint whose `rtrim(url,'/')` equals the audit mint url or an alias in `audit_cz_aliases`; a detail without both numbers writes NULLs. Untrusted detail strings are never used in the score: only two validated non-negative integers.

### mint_audit_swaps (added 2026-09-12 — per-swap audit.8333.space detail)
```
url TEXT REFERENCES mints(url) ON DELETE CASCADE
swap_id BIGINT NOT NULL           -- audit.8333.space's own per-swap id
to_url TEXT
amount INTEGER
fee INTEGER
created_at TIMESTAMPTZ
time_taken_ms DOUBLE PRECISION
state TEXT NOT NULL
error TEXT                        -- nullable
PRIMARY KEY (url, swap_id)
```
Index: (url, created_at DESC). Populated by the same 6h discovery cron that already fetched
`GET /swaps/mint/{id}` for the rolling `audit_recent_total`/`audit_recent_errors` counters
(`discovery.ts`'s `fetchRecentSwaps`/`persistMintAuditSwaps`) — that call previously read only
the `state` field and discarded everything else; it now parses the full item (confirmed live
shape: `id, from_id, to_id, from_url, to_url, amount, fee, created_at, time_taken, state, error`)
via `parseAuditSwapItem()` and stores the last ≤100 swaps per mint. **Fully replaced** (DELETE +
batched multi-VALUES INSERT + the `mints` summary-column UPDATE, all in one transaction — same
atomic-per-mint-replace pattern as `mint_reviews`/`persistMintReviews`) every cycle, so this table
only ever holds each mint's *current* window, not swap history across cycles. `computeSwapStats()`
derives `total`/`errors` (unchanged from before) plus the new `avgTimeMs` (mean `time_taken` over
`state === 'OK'` swaps with a known time; `null` if none). Parsing is defensive — only `id`/`state`
are required, a missing/wrong-typed `time_taken`/`to_url`/etc. degrades that field to `null`
instead of dropping the swap or failing the cron. **Backend-only as of this addition** — no Mint
Detail UI reads this table or `auditAvgTimeMs` yet; the frontend still never calls audit.8333.space
directly (SSRF surface unchanged). Tests: `backend/src/__tests__/discoveryAuditSwaps.test.ts`
(parser + `computeSwapStats` + `persistMintAuditSwaps` transaction shape, using two real
anonymized sample payloads captured from a live diagnostic GET against the Minibits mint id) +
`integration/mints-swaps.test.ts`.

### Pool errors: the database connection (2026-10-16)

`pool` (`backend/src/db.ts`, the only `new Pool` in the backend; there is no `new Client`) has an `'error'` listener, attached by `attachPoolErrorHandler()`. **Why:** the pg Pool emits `'error'` when an IDLE client loses its connection (Postgres restart, container recreation, network drop; after the 2026-10-16 server reboot it was 5 times `terminating connection due to administrator command`, code `57P01`, one per idle client). With no listener Node turns each into an `uncaughtException`; only the process-level handlers in `index.ts` (last resort, unchanged) kept the process alive. The listener only logs, because pg removes the failed client from the pool itself and connects anew on the next query. **Log:** one line `[db] pool error: <message> (code <code>)` (message cut to 200 characters, anything that looks like a URL replaced by `[redacted-url]`, never SQL or parameters), at most one per 10 seconds, followed by one line `[db] pool error: N more in the last 10s (suppressed)` when repeats were swallowed. No change to pool size, timeouts or retries. **Rule:** every long-lived pg `Pool` or `Client` needs such a listener (call `attachPoolErrorHandler` on it). A query that is RUNNING when its backend is killed rejects with `57P01`; it does not reach the listener, so its caller's `catch` decides (request handlers and the cron jobs catch; see the report of this change for the exceptions). Tests: `dbPoolErrors.test.ts` (fake emitter: listener attached, no throw, redaction, rate limit with fake timers) and `dbPoolErrors.pg.test.ts` (real Postgres, skipped unless `MR_PG_TEST_URL` is set: kills idle backends and a running query, expects no uncaughtException and a working next query).

## Backend API
- GET /health and GET /api/v1/health — health check (same payload, both rate-limit exempt; the `/api/v1` prefix rewrite has a special case mapping it to `/health`; there is deliberately NO `/api/health`). Payload: `status, timestamp, lastProbeAt, lastAuditSyncAt, lastReviewsSyncAt, auditUpstream, auditUpstreamCheckedAt`. `auditUpstream` (`ok|down|unknown`) is module-level in-memory state in `discovery.ts` set by `discoverMintsFromApi()` (last sync attempt, not a live check; `unknown` after restart until the next 6h sync); `/health` makes no outbound request. `getSyncTimesFromDb()` dedupes concurrent queries on cache expiry
- GET /api/mints/known — all mints with online status, latency, reliability score, degraded flag (TTL cached 60s). Each mint carries `softwareLatest` (`{ major, minor }` of its own software family, `null` for unknown software — the ONE "latest" from `versionCatalog.ts` `getLatestVersionsMap()`, see docs/claude/scoring-and-probing.md); `/api/mints/version-history` still returns the same value as `latestGlobalVersion` (`nutshell/0.21`)
- **Wallet API v1 (2026-10-12, `backend/src/walletApi.ts`, contract in `docs/API.md` "API for wallets (v1)" and `docs/openapi/wallets-v1.yaml`):** `GET /api/wallets/mints` (list, filters `unit`, `minScore`, `includeOffline|Test|Archived|Unscored`, `limit` ≤ 200) and `GET /api/wallets/mints/<percent-encoded url>` (normalised with `normalizeUrl`, `isWellFormedMintUrl`, no DNS), reachable as `/api/v1/wallets/…` through the existing rewrite. A pure view of the `/api/mints/known` snapshot: `loadKnownMints()` in `index.ts` is the ONE computation (60 s cache plus an in-flight promise, so at most one database read per minute for `/known`, the wallet API and `/api/mints/recommend` together; `invalidateKnownMints()` replaces the old `knownMintsCache = null`). The mint object has exactly the keys of `WalletMint` (names fixed for v1: additive changes only; a contract test lists the key set and scans for IP/network/onion/pubkey/contact/review-text data). `methodology` comes from `shared/methodology.ts` (`METHODOLOGY_VERSION`, `METHODOLOGY_CHANGES`; bump both in the SAME commit as any formula change; since 2026-10-13 a byte-identical frontend copy `src/utils/methodology.ts` feeds the `/methodology` page, see `methodology-and-wallet-pages.md`; the mint object's field list `WALLET_MINT_FIELDS` lives in `shared/walletFields.ts` and a test compares it with the mapper). Errors of these routes: `{ error: { code, message, retryAfterSec? } }`; every other route keeps `{ error: "text" }`.
- **`GET /api/mints/recommend` (2026-10-12):** `recommendEnvelope()` in `walletApi.ts` over the same snapshot and `filterWalletMints` as the wallet API, with `eligibleOnly` (`eligibleForRecommendation` = online + scored + not `isTestMint` + not archived + `isEligibleForRecommendation`, the 14-day gate). Before this it ran its own SQL and listed test mints and brand-new mints. Shape unchanged plus `methodology`; `generatedAt` = snapshot time; limit (max 10) is applied AFTER the nuts filter (the old SQL cut first). Since 2026-10-13 it is on the wallet limiter (300/min/IP, ONE counter shared with `/api/wallets/*`, `usesWalletRateLimit()` in `walletApi.ts`; its 429 keeps the old `{ error: "Too many requests" }` body, with the same `X-RateLimit-*` and `Retry-After`); the rest keeps the old `{ error: string }` shape.
- **CORS (middleware in `index.ts`, after the `/api/v1` rewrite):** `Access-Control-Allow-Origin: *` (GET, HEAD, OPTIONS, no credentials, exposed headers ETag, Retry-After, X-RateLimit-*) ONLY for `/api/wallets/*`, `/api/mints/known`, `/api/mints/recommend` and `/health` (`isPublicCorsPath`); preflight = 204 before the rate limiter. Every other route keeps the `ALLOWED_ORIGINS` list, and a foreign `Origin` there is a JSON `403 { error: { code: "cors_forbidden" } }` (it used to be Express's HTML 500). Adding a route to the public list is a security decision: read-only, cacheable, no personal data.
- **Caching (`sendCachedBody`):** `/api/mints/known`, `/api/wallets/*` and `/api/mints/recommend` send `Cache-Control: public, max-age=300` and a strong ETag (sha256 of the body, memoised per snapshot) on every response, hit or miss; `If-None-Match` → 304. `generatedAt` is the snapshot time, not `now`, so the ETag stays stable within a snapshot. Since 2026-10-13 the shared-data website routes `/api/stats`, `/api/stats/reliability-movers`, `/api/mints/swaps`, `/api/mints/audit-cz` and `/api/mints/nostr-reviews` use it too with their OWN max-age (60 s / 600 s / 300 s / 60 s / 120 s; `sendCachedBody(res, body, maxAgeSec)`, `cachedBodyOf(data)` memoises the body of the stats caches per data object) instead of `max-age=N` + Express's weak ETag. NOT shared: submit, probe, notifications; `/api/og/mint` (HTML for bots) still has its own `max-age` without `public`.
- **Rate limits:** the general limiter is 60/min/IP (exempt: `/health`, `/api/mints/known`, `/api/stats`, `/api/mint/icon`); `/api/wallets/*` and `/api/mints/recommend` share their own counter, 300/min/IP (`WALLET_RATE_LIMIT_MAX`, `usesWalletRateLimit()`); both send `X-RateLimit-Limit/Remaining/Reset`, and EVERY 429 (general, wallet, submit, discover, notifications, unknown-URL probe) sends `Retry-After`. Stores are in memory and purged every window.
- GET /api/mints/history?url=&period={24h|7d|30d|90d} — bucketed uptime/latency segments + prev period trend
- GET /api/mints/version-history?url= — per-mint software version timeline + latest global version
- GET /api/mints/daily-uptime?url= — daily uptime counts for last 30 days
- GET /api/mints/audit-cz?url= — cashu.info data for one mint from `audit_cz_*` (see tables above). Same url validation as `/api/mints/swaps`. Query: `url` (required), `direction` = `from` | `to` | `both` (default `both`; anything else, empty or repeated → 400 `direction must be from, to, or both`), `limit` (1..100, default 20; decimals rounded down, ≤0 → 1, non-numeric/repeated → 20). Always 200 for a valid url (400 for a bad url/direction, 500 on a server error): `covered:false` + `mint:null` + `swaps:[]` + `stats7d:null` (no `detail` key) when not in their feed; otherwise `mint` (state/uptimes/attributedFailures/minted/melted/lastCheck), up to `limit` newest swaps for the chosen direction (`from` = this mint is the source, `to` = destination, `both` = either; a swap with both sides matching is returned once, as `from`), and `stats7d` (counted by MintRadar over the last 7 days, both directions, unaffected by `limit`/`direction`). Also `detail` (see the next bullet; the old on-demand `detail7d` and its cache were removed). Full field reference: `docs/API.md`. `Cache-Control: max-age=60`; normal per-IP rate limit. Display only — never merged into any MintRadar number.
- GET /api/mints/audit-cz also returns `detail` (covered mints only; the validated subset stored by the detail cron plus `fetchedAt`, or `null` when none is stored yet; read from `audit_cz_detail` only, no outbound request) (the old derived `detail7d` was removed with the new Audit tab).
- GET /api/mints/swaps?url= — the audit.8333.space rolling-window swap detail (`mint_audit_swaps`, ≤100 rows) for one mint plus `avgTimeMs`. Added 2026-09-12, deliberately kept OUT of `/api/mints/known` (which is fetched on every Dashboard load for every mint — embedding the full per-mint swap list there would multiply that payload ~65x for a feature only a not-yet-built Mint Detail view would use); `/api/mints/known` gains only the small scalar `auditAvgTimeMs`. Same url validation (`https://`, `MAX_URL_LENGTH`, `isWellFormedMintUrl` — syntactic, no DNS) as `/api/mints/history`\|`version-history`\|`daily-uptime`. `Cache-Control: max-age=300`. No frontend UI reads this endpoint yet.
- **Which endpoints resolve DNS for the mint URL, and why (2026-10-04):** `isSafeUrl()`/`checkUrlSafety()` (`ssrf.ts`) resolve the host and answer `dns-error` when it has no DNS record. They are for endpoints that make an **outbound request** to a user-supplied host and must stay exactly as they are: `GET /api/mint/probe` (via `probeMint`/`safeFetch`), `POST /api/mint/submit`, `POST /api/mints/discover`, `GET /api/mint/icon`, `GET /api/nip05/verify` (`safeFetch`), `POST /api/notifications/subscribe` (`checkWsUrlSafety` on relay URLs). Endpoints that only **read our own database** — `GET /api/mints/history`, `version-history`, `daily-uptime`, `swaps`, `audit-cz` — use `isWellFormedMintUrl()` (`ssrf.ts`): no DNS, no network; https only, ≤500 chars, no whitespace or credentials, a parseable URL, either a host name that looks like one (≥2 labels of `[a-z0-9_-]`, ≤63 chars each) or an IP literal that is NOT in a range `isBlockedAddress()` blocks (the URL parser already folds decimal/hex/octal IPv4 into dotted quads; bracketed IPv6 is classified too). Before this, a stored mint whose DNS record was gone (e.g. `mint.lnwallet.app`, `mint.0xchat.com`) answered `400 Invalid url` and its stored data could not be loaded. A syntactically valid host that is simply dead now gets the normal data or the normal empty answer; syntactically invalid URLs and blocked IP literals still get the same `400 {"error":"Invalid url"}`. `GET /api/mints/nostr-reviews` never had a DNS check (only `https://` + length) and is unchanged. Rule for new endpoints: if the handler makes no outbound request to the supplied host, validate with `isWellFormedMintUrl()`; if it does, use the DNS-resolving guard / `safeFetch`.
- GET /api/stats — network-wide stats: totalMints, onlineMints, offlineMints, avgReliabilityScore, avgLatency24h, reliabilityDistribution, nutAdoption, top5ByReliabilityScore
- GET /api/stats/reliability-trend?days={30|90} — daily network-average Reliability Score (Stats trend chart). Cached in process 10 min per period (`public, max-age=600`), warmed at startup and refreshed every 9 min, concurrent misses share one query; the underlying aggregate is a ~1.3 s seq scan of `mint_history` (see `stats-dashboard-watchlist-ui.md`, "Reliability Score trend").
- GET /api/stats/reliability-movers?period={7d|30d} — Reliability Score risers/fallers (Stats page). As of 2026-09-01 a plain read of `mints` (`last_reliability_score` + `reliability_score_{7,30}d_ago` rollup columns), NOT the old two `DISTINCT ON` passes over all of `mint_history` (~2.5s cold — the "old" CTE had no time bound and `reliability_score IS NOT NULL` was unindexed). Rollup is refreshed by `refreshReliabilityMoversRollup()` (`backend/src/reliabilityMoversRollup.ts`) on the 5-min probe cron + ~15s after boot; partial index `idx_mint_history_score_checked ON mint_history(url, checked_at DESC) WHERE reliability_score IS NOT NULL` backs its point-in-time lookups. In-memory cache TTL 10min (own `RELIABILITY_MOVERS_CACHE_TTL`, not `KNOWN_MINTS_CACHE_TTL`). +/-3 threshold + top-3 ranking in `reliabilityMovers.ts` (`computeReliabilityMovers`). Frontend panel (`src/components/stats/ReliabilityMoversPanel.tsx`) takes `loading`/`refreshing` props — skeleton while pending, `keepPreviousData` across the 7d/30d toggle; "No data yet" shows only for a settled-but-empty result.
- GET /api/mint/probe?url= — on-demand probe of a single mint URL (unauthenticated, SSRF-guarded). **Unknown-URL rate limit (2026-10-03):** the handler runs the `SELECT 1 FROM mints` lookup FIRST (no longer in parallel with the probe — a tracked mint costs one extra DB round-trip), and only for a URL that is NOT tracked calls `tryAcquireUnknownProbe(ip)` before any outbound fetch: per IP 10/min (`UNKNOWN_PROBE_PER_MINUTE_MAX`) + 60/hour (`UNKNOWN_PROBE_PER_HOUR_MAX`) fixed windows (`unknownProbeMinuteStore`/`unknownProbeHourStore`, same `RateLimitEntry` pattern, own 60 s sweep) + at most 3 in flight (`unknownProbeInFlight`, incremented before the probe, decremented in a `finally` via `releaseUnknownProbe` — an aborted client does not cancel the probe, so the slot is held until `probeMint` settles, bounded by the 12 s deadline; it never leaks). Over any limit → `429 {"error":"Too many requests. Try again later."}` + `Retry-After` (seconds until the blocking window resets, max of both if both are full; fixed `5` for the concurrency cap); a rejected request consumes no budget. Tracked mints: global limiter only. In-memory, a restart resets it. Frontend: the Submit modal Single preview shows `probeRateLimitMessage(Retry-After)` (`src/utils/probeErrorMessages.ts`: ≤45 s → "N seconds", 46–90 s → "a minute", >90 s → "N minutes", missing header → "Try again in a moment") in `.submit-probe-error`, keeps the input, never auto-retries, button stays disabled; it is NOT `errorKind rate_limited_by_host`. Mint Detail's proxy probe (`api.ts`, `probeMintViaProxy`) THROWS on any non-OK answer, network error, timeout or malformed body (since 2026-10-17; before, it turned them into `online:false` / "Mint unreachable", which `useMintProbe` also wrote to the local history as an offline check): the failure is not a mint state. Mint Detail then keeps rendering from the stored mint and shows `LoadError` with `LIVE_DATA_ERROR` and Try again (`refetch`) in the Mint info panel; only a `200` with `online:false` is an offline mint. **Response scope (2026-09-07 audit L5):** for a mint already in `mints` the full live `/v1/info` + keysets are returned (Mint Detail needs it; the cron already probes those hosts continuously). For any OTHER url only `online` / `latencyMs` / `checkedAt` + a stripped `info` (`name`, `version`, `nuts` with keys only — enough for the Dashboard submit preview) are returned, and `keysets: null` — so it can't be used as a general "fetch and echo the JSON body of arbitrary public host X" oracle. **Failure classification (`errorKind`, 2026-10-03):** `error` stays the literal `"Mint unreachable"`; a failed probe additionally carries `errorKind` — an enum from `backend/src/probeErrorKind.ts` (`blocked_by_host | rate_limited_by_host | host_error | timeout | dns | tls | not_cashu | unreachable`), decided by the pure `classifyProbeFailure()` from the HTTP status + three header facts (`cf-mitigated` present, `server`, `content-type`) or, for network failures, the label of `classifyFetchError()` (`prober.ts`, now exported). `probeMint` collects the cause via `safeFetch`'s `onError` and its new `onRejected` callback (SSRF guard / DNS / bad-redirect refusals, which used to return `null` silently; `onError` semantics are unchanged so the cron's `last_error` is unaffected). Details, constants and the REQ numbers in `docs/claude/reviews-and-nostr.md` "Reviews sync". `wss://relay.nostr.net` is back on `DISCOVERY_RELAYS` and `REVIEW_SYNC_RELAYS` as of 2026-09-27; it stays off `REVIEW_READ_RELAYS`.
- Daily 3:15am: `pruneUnvalidatedMints()` — deletes rows discovered >168 hours (7 days, `UNVALIDATED_CANDIDATE_TTL_HOURS`) ago that NEVER had a successful probe (covers any insert path that skips `isValidCashuMint()`); then `pruneAbandonedMints()` — deletes once-online mints whose `last_online_at` is older than 90 days (`ABANDONED_REAP_DAYS`, same as the history retention).
  - **Seeded mints stay pruned (2026-10-09):** the hardcoded `KNOWN_MINTS` are inserted only once per database (`app_state` key `known_mints_seeded`, see docs/claude/discovery-and-relays.md); before that the seed re-inserted pruned dead mints at every process start.
- Daily 3:45am: refresh `software_versions` cache from the GitHub Releases API (`cashubtc/nutshell`, `cashubtc/cdk`) — see Reliability Score calculation above
- Daily 4:45am: `refreshReviewSurgeBaseline()` (`backend/src/reviewSurgeRollup.ts`) — advances the rolling `review_count_7d_ago` snapshot for any mint whose snapshot is missing or ≥7 days old (skips mints whose `review_count` is still NULL, so the first reviews-sync never looks like a surge). Also primed 60s after boot. Single-flight, never throws. Feeds the `reviewSurge` field on `/api/mints/known`.
- Daily 4:15am: `revalidateMints()` (`backend/src/prober.ts`) — **recurring Cashu-content revalidation** (fix for the "validate once at submit, then DNS/redirect-repoint anywhere" confused-deputy finding). Per mint, a STRONGER check than the 5-min probe: `/v1/info` must have a **non-empty** `nuts` object AND `/v1/keys` must return ≥1 keyset. Tri-state result — `ok` / `not-a-mint` / `unreachable`. `not-a-mint` (a repoint target: HTML page, redirect, `{"nuts":{}}` stub, 4xx) sets `mints.invalid_since = COALESCE(invalid_since, NOW())`; `ok` clears it; `unreachable` (5xx / timeout / DNS) leaves it untouched so a genuine multi-day outage never counts. The 5-min probe (`probeMintToDb`) also maintains `invalid_since` for the reachable-but-not-a-mint case (`lastError` ∈ {`Invalid Cashu response`, `Invalid JSON response`, `HTTP 4xx`}). Any mint with `invalid_since` older than **`REVALIDATION_REAP_DAYS` (7)** is `DELETE`d — removed from the probe rotation entirely, bounding the confused-deputy window from "forever" to ≤7 days. The 5-min probe already flips such a mint offline within minutes (dropping it from recommendations / marking it degraded); this job is what eventually removes it. **The lenient `isValidCashuMint()` submit/discovery gate is deliberately NOT tightened** — only this new sweep uses the stronger criteria, so an unusual-but-real mint is never rejected at submit time.


### Server location refresh (2026-10-07)
`mints.server_location` ("City, CC") comes from ipinfo.io for the mint host's address (IPv4 first, `lookupGeo` in `prober.ts`). It used to be resolved only while NULL, so a mint that moved hosts kept its first city (cashu.cz showed Toronto after moving to Frankfurt). `refreshServerLocations()` now re-resolves EVERY mint once after boot (+120 s) and daily at 05:30 (`cron.ts`, skipped in allowlist mode): one ipinfo request per mint, sequential, 150 ms apart; a changed result overwrites, a failed lookup (timeout, bogon, no data) changes nothing. The city is where ipinfo places the IP, not the registry country (which can differ, e.g. DigitalOcean blocks are registered in the US) and not where the operator is. The same ipinfo answer also feeds the Network card (2026-10-07): `lookupGeo()` returns `{ location, asn, org, country }` and `storeNetwork()` writes `mints.net_asn` / `net_org` (parsed from `org` "AS14061 DigitalOcean, LLC" by `parseIpinfoOrg`, 80 chars max) / `net_country` (ISO code) — one request per mint, no extra traffic; `backfillServerLocations()` also picks mints with `net_country IS NULL`. `mints.has_onion` is set by `probeMintToDb` on every successful probe from `/v1/info` `urls` (boolean only). All four are served by `GET /api/mints/known` as `netAsn` / `netOrg` / `netCountry` / `hasOnion`. Test: `__tests__/refreshServerLocations.test.ts`.

## Network layer: SSRF rules, relay connections, icon proxy (2026-10-14)

**Rule: every outbound connection to a host that is not hard-coded goes through the safe wrappers in `backend/src/ssrf.ts`.** HTTPS: `safeFetch` (validates the URL and every redirect hop, connects through `safeLookup`, one deadline, no credentials) and `readBodyLimited` / `readJsonLimited` (size caps). Relay sockets that are not hard-coded: `DnsPinnedWebSocket` (nostrService.ts, `lookup: safeLookup`). Subscriber-supplied relay URLs are checked once with `checkWsUrlSafety` on subscribe and again at connect time by the pin. Known exceptions, deliberately: the hard-coded relay lists (`DISCOVERY_RELAYS`, `REVIEW_SYNC_RELAYS`, ...) used by discovery.ts (root `SimplePool`) and reviewsRelayFetch.ts do not go through the DNS pin; a dynamic list there must be switched to the pinned socket first.

| Rule (ssrf.ts) | What it does |
|---|---|
| Scheme allow-list | `checkUrlSafety`: `https:` only; `checkWsUrlSafety`: `ws:` / `wss:` only; everything else (`http`, `file`, `ftp`, `gopher`, `data`, `javascript`, `blob`, scheme-relative, empty) → `blocked` before any lookup |
| URL length | over 500 characters → `blocked` |
| Port | relays: `wss` only on 443, `ws` only on 80 (`isAllowedRelayPort`, before DNS); mints: any valid port on a public host (mints run on 3338, 8085, ...), an invalid port → `blocked` |
| Address ranges | `isBlockedIpString` / `isBlockedAddress`: loopback, private, link-local (incl. 169.254.169.254), unique-local, unspecified, reserved (TEST-NETs, benchmarking 198.18/15, 192.0.0/24, 240/4), CGNAT 100.64/10, broadcast, **multicast, discard 100::/64, benchmarking 2001:2::/48, site-local fec0::/10** (the last four since 2026-10-14) |
| IPv4 inside IPv6 | unwrapped and re-checked: IPv4-mapped, NAT64 64:ff9b::/96, 6to4, Teredo (XOR), IPv4-translated ::ffff:0:0:0/96; never public at all: IPv4-compatible `::/96` (`https://[::127.0.0.1]` is printed by the URL parser as `[::7f00:1]`) and RFC 8215 `64:ff9b:1::/48` |
| IP-literal notations | the WHATWG URL parser folds decimal / hex / octal / short forms and unicode dots into dotted quads before the check, so the host that is checked is the host the socket uses; tests compare `new URL(x).hostname` |
| DNS policy | public answers only → `safe`; any blocked or unparseable address in the set → `blocked`; resolver error or empty answer → `dns-error` (not an SSRF signal, never `safe`); nothing is cached |
| DNS time limit (2026-10-16) | a resolver that never answers is cut off: `DNS_LOOKUP_CEILING_MS = 3_000` (`ssrf.ts`) is the most the DNS step of ONE request may take, all its lookups together (a redirect hop's lookup gets what the earlier ones left, not a fresh 3 s). **One deadline:** `safeFetch` passes a `DnsBudget` (`deadlineAt` = start + `timeoutMs`, `dnsUsedMs`) to every `checkUrlSafety`, so DNS time counts against the SAME `timeoutMs` as the fetch (DNS 2 s + hanging fetch → aborted at 5 s total, not 7 s); each lookup gets `min(time left to the deadline, 3 s - DNS time already used)`, nothing left → `dns-error` without asking the resolver. A standalone `checkUrlSafety` / `checkWsUrlSafety` gets the ceiling only. **Fail closed:** a timeout is the ordinary `dns-error` outcome (no new `UrlSafetyResult`, `onRejected` still says `'dns-error'`, the probe records the mint offline with 'DNS resolution failed', relay validation stores the relay like any dns-error relay, `isSafeUrl` is false); it is told apart only by the log line `[ssrf] dns-timeout` (no host name) and is never cached. The timer is cleared on every path and the abandoned lookup has a `.catch`, so a late answer or rejection cannot become an `unhandledRejection`. The connect-time pin (`safeLookup`, used by undici and `DnsPinnedWebSocket`) has the same 3 s bound (error `code: 'ETIMEOUT'`, late answer dropped). Not covered, deliberately: `resolve4` in `mintAddress.ts` and the geo lookup in `prober.ts` are display-only, not SSRF checks |
| Rebinding | validation resolves once (`dns/promises`), the connection resolves through `safeLookup`, which re-checks the very answer the socket then uses; nothing resolves a third time |
| Redirects | followed by hand, max 3 hops, every hop re-validated (`checkUrlSafety`), relative `Location` resolved against the current URL, a missing / unparseable `Location` → `bad-redirect` |
| Limits | one `AbortSignal.timeout` for the whole call (not per hop); caps in `RESPONSE_CAPS`, `Content-Length` pre-check plus counting while streaming; honest `User-Agent: MintRadar/1.0 (+https://mintradar.org)` |

Tests (no real network, no real DNS; lookups and undici are stubbed, the one real socket is a stub server on 127.0.0.1 that must stay untouched): `backend/src/__tests__/ssrfAddresses.test.ts` (ranges, IPv6 embeddings, URL notations, parser differentials), `ssrfDns.test.ts` (schemes, ports, host forms, DNS policy, `safeLookup`, rebinding), `ssrfFetch.test.ts` (redirects, deadline, body limits), `ssrfDnsTimeout.test.ts` (DNS ceiling, shared deadline, no dangling timers / unhandledRejection, pinned path; fake timers), `ssrfCorpus.test.ts` (every configured relay and a sample of real mints must stay allowed), plus the older `ssrfGuard.test.ts`. **To add a case:** put one row in the matching table (`V4` / `V6` in ssrfAddresses, `NOTATIONS`, the `BAD` lists in ssrfDns) with the expected verdict; for a new rule change `ssrf.ts` and add a row that fails without it. A new relay or mint host that the guard wrongly blocks shows up in `ssrfCorpus.test.ts`. Coverage of `ssrf.ts`: 100 % lines, 99 % branches (`npx vitest run --coverage --coverage.include=src/ssrf.ts`).

**Relay connections: never leave a promise or an error event floating.** nostr-tools closes a socket that is still CONNECTING when its connection timeout (3 s) fires and nulls `onerror` straight away; `ws` then emits `error` with no listener and Node raised `uncaughtException: WebSocket was closed before the connection was established` once per start (discovery at +10 s, the service profile at start). Fixed at the source: every nostr-tools pool connects with `RelayWebSocket` (`wsPolyfill.ts`, a `ws` subclass with a permanent no-op `error` listener; `DnsPinnedWebSocket` extends it). The process-level `uncaughtException` / `unhandledRejection` handlers in `index.ts` stay as a last resort for unexpected errors and only log; they are not what handles this case (and, since 2026-10-14, they are registered in the not-under-test start block, next to SIGTERM/SIGINT, not at import). Rules for relay code: attach `error` / `close` listeners before the socket is used; bound every connection with a timeout; `Promise.allSettled` over several relays; give a floating `publish()` promise a `.catch`; close in `finally` (`pool.destroy()`, `conn.close()`). `relayConnectionErrors.test.ts` runs the four call sites (`publishToRelays`, the attestation pool publisher, the root `SimplePool` of discovery.ts, `connectRelayWs`) against a stub relay that refuses, accepts and stays silent, closes at once, sends a close frame or invalid frames, and asserts no uncaught exception, no unhandled rejection (listened for 200 ms after the call), a bounded duration and no socket left. Separate nostr-tools problem, not reachable here: with Node's NATIVE WebSocket a failed connection recurses (`RangeError: Maximum call stack size exceeded`, onerror -> close -> error); the backend uses `ws` for that reason, standalone scripts must set `useWebSocketImplementation(ws)` too. nostr-tools 2.25.2 (latest on 2026-10-14) still has both.

The frontend treats `iconUrl` only as a "has icon" hint and drops to the monogram on `<img onerror>`.
