### mint_reviews (added 2026-08-30 — review-load perf work)
```
url TEXT REFERENCES mints(url) ON DELETE CASCADE
pubkey TEXT NOT NULL
event_id TEXT NOT NULL
rating INTEGER            -- null for rating-less endorsement events
comment TEXT NOT NULL DEFAULT ''   -- capped at 2000 chars on write
created_at BIGINT NOT NULL         -- nostr event created_at (unix seconds)
PRIMARY KEY (url, pubkey)          -- one row per author per mint, newest wins
```
Index: (url, created_at DESC). Populated by the hourly reviews sync (`backend/src/reviewsSync.ts`).
`reviews_sync_relay_state` (relay TEXT PK, `last_ok_started_at` BIGINT NULL (NULL = counters row of a relay that never finished a clean run; ignored by the sync), `last_full_at` BIGINT NULL; unix seconds) — per-relay progress of that sync: when the last clean run on the relay started and when the last full sweep did. Drives the `since` of the next incremental query. Since 2026-10-13 the same row also holds per-relay delivery counters (`runs`, `ok_runs`, `failed_runs`, `skipped_runs`, `events_delivered`, `events_exclusive`, `events_new`, `total_ms`, `last_run_exclusive`, `counters_since`; counts only, see "Relay delivery counters" in `docs/claude/reviews-and-nostr.md`); see "Reviews sync" in `docs/claude/reviews-and-nostr.md`.
Rollup columns on `mints`: `review_count INTEGER`, `review_avg_rating REAL`, `reviews_checked_at TIMESTAMPTZ`.
`review_count_7d_ago INTEGER` + `review_count_7d_ago_at TIMESTAMPTZ` — rolling ~1-week-ago `review_count` snapshot, advanced once a day (`reviewSurgeRollup.ts`); feeds the informational "recent review surge" sybil flag (see Reviews Feature below).

### audit_cz_mints / audit_cz_aliases / audit_cz_swaps (added 2026-10-04 — cashu.info, formerly audit.cashu.cz, display only; the table names, the `source` value and the endpoint path keep the historical name on purpose)
Second, public audit source (`backend/src/auditCz.ts`). **These three tables stay display only**: the prober and `/api/mints/known` never read them. Since 2026-10-08 two numbers of the per-mint detail reach the Reliability Score, but through `mints.audit_cz_*` (see `audit_cz_detail` below), never from these tables at probe time. No FK to `mints`; no row is ever created in `mints` from this source.
```
audit_cz_mints(url PK [normalised], state ok|warn|error, uptime24h, uptime7d, uptime30d DOUBLE, attributed_failures INT, minted INT, melted INT [their list feed's counts, nullable],
               last_check TIMESTAMPTZ, page TEXT [https://cashu.info/mint/<id>, BUILT by `auditCzPageUrl(id)` from the feed id after `^[A-Za-z0-9]{8,64}$`; never the feed's own `page`; a boot migration in `db.ts` rewrites rows that still hold https://audit.cashu.cz/mint/<id> (idempotent)], fetched_at, source='audit.cashu.cz')
audit_cz_aliases(alias_url PK, mint_url, fetched_at)      -- their aliases[], normalised
audit_cz_swaps(id TEXT PK, at, status short lowercase token (success, failed, pending, or any other `^[a-z][a-z_-]{0,29}$` token the source sends), stage short lowercase token (melt, mint, balance, limits, …) or NULL, error ≤300 chars,
               amount, fee, duration_ms, from_url, to_url, from_name, to_name, fetched_at, source)
  indexes: (from_url, at DESC), (to_url, at DESC), (at DESC)
```
Keys use `normalizeUrl()` plus a stripped trailing slash (`auditCzKey`); a tracked mint matches when its key equals their `url` or any alias (our DB has no alias data of its own — `aliasOf` is only a submit/discover hint). Swaps are stored as given and matched at read time (from or to) through the same url+aliases set. Sync: upserts, one transaction per response; any failure (timeout, HTTP error, >1 MiB, bad JSON, bad top-level shape) writes and deletes nothing; malformed items are skipped; pruning (>14 days, hard cap 20000 rows) only after a successful swaps write.

### audit_cz_detail (added 2026-10-07 — cashu.info per-mint detail; display, plus two numbers copied to `mints.audit_cz_*` for the Reliability Score since 2026-10-08)
```
audit_cz_detail(url TEXT PK [= audit_cz_mints.url], detail JSONB [validated subset only: swaps7d {all/asSource/asDest {total,success,failed,avgMs}, errorsBlamed, dleq}, integrity {proof_state {checked,spent,pending}}, network {asn, asName, country}, onion (boolean); pruned 2026-10-07: step timings, swap_test, TLS, ipv4/ipv6 flags, latency], fetched_at)
```
Never stored: score, scoreParts, reviews, daily, changes, incidents7d, Frankfurt data, spec details (the onion address becomes a boolean). The only IP kept anywhere is the mint host's own public IPv4, resolved by us into `mints.ip_address` (`mintAddress.ts`, boot + every 6 h), never the source's data. Written only by `syncAuditCzDetails()` (`backend/src/auditCzDetail.ts`); a failed fetch writes and deletes nothing. The same statement (a CTE: upsert + `UPDATE mints`) copies `swaps7d.all.total`, `swaps7d.errorsBlamed` and the fetch time to `mints.audit_cz_total` / `audit_cz_blamed` / `audit_cz_fetched_at` of every tracked mint whose `rtrim(url,'/')` equals the audit mint url or an alias in `audit_cz_aliases`; a detail without both numbers writes NULLs. Untrusted detail strings are never used in the score: only two validated non-negative integers.

### mint_audit_swaps (added 2026-09-12 — per-swap audit.8333.space detail)
```
url TEXT REFERENCES mints(url) ON DELETE CASCADE
swap_id BIGINT NOT NULL           -- audit.8333.space's own per-swap id
to_url TEXT
amount INTEGER
fee INTEGER
created_at TIMESTAMPTZ
time_taken_ms DOUBLE PRECISION
state TEXT NOT NULL
error TEXT                        -- nullable
PRIMARY KEY (url, swap_id)
```
Index: (url, created_at DESC). Populated by the same 6h discovery cron that already fetched
`GET /swaps/mint/{id}` for the rolling `audit_recent_total`/`audit_recent_errors` counters
(`discovery.ts`'s `fetchRecentSwaps`/`persistMintAuditSwaps`) — that call previously read only
the `state` field and discarded everything else; it now parses the full item (confirmed live
shape: `id, from_id, to_id, from_url, to_url, amount, fee, created_at, time_taken, state, error`)
via `parseAuditSwapItem()` and stores the last ≤100 swaps per mint. **Fully replaced** (DELETE +
batched multi-VALUES INSERT + the `mints` summary-column UPDATE, all in one transaction — same
atomic-per-mint-replace pattern as `mint_reviews`/`persistMintReviews`) every cycle, so this table
only ever holds each mint's *current* window, not swap history across cycles. `computeSwapStats()`
derives `total`/`errors` (unchanged from before) plus the new `avgTimeMs` (mean `time_taken` over
`state === 'OK'` swaps with a known time; `null` if none). Parsing is defensive — only `id`/`state`
are required, a missing/wrong-typed `time_taken`/`to_url`/etc. degrades that field to `null`
instead of dropping the swap or failing the cron. **Backend-only as of this addition** — no Mint
Detail UI reads this table or `auditAvgTimeMs` yet; the frontend still never calls audit.8333.space
directly (SSRF surface unchanged). Tests: `backend/src/__tests__/discoveryAuditSwaps.test.ts`
(parser + `computeSwapStats` + `persistMintAuditSwaps` transaction shape, using two real
anonymized sample payloads captured from a live diagnostic GET against the Minibits mint id) +
`integration/mints-swaps.test.ts`.

### Pool errors: the database connection (2026-10-16)

`pool` (`backend/src/db.ts`, the only `new Pool` in the backend; there is no `new Client`) has an `'error'` listener, attached by `attachPoolErrorHandler()`. **Why:** the pg Pool emits `'error'` when an IDLE client loses its connection (Postgres restart, container recreation, network drop; after the 2026-10-16 server reboot it was 5 times `terminating connection due to administrator command`, code `57P01`, one per idle client). With no listener Node turns each into an `uncaughtException`; only the process-level handlers in `index.ts` (last resort, unchanged) kept the process alive. The listener only logs, because pg removes the failed client from the pool itself and connects anew on the next query. **Log:** one line `[db] pool error: <message> (code <code>)` (message cut to 200 characters, anything that looks like a URL replaced by `[redacted-url]`, never SQL or parameters), at most one per 10 seconds, followed by one line `[db] pool error: N more in the last 10s (suppressed)` when repeats were swallowed. No change to pool size, timeouts or retries. **Rule:** every long-lived pg `Pool` or `Client` needs such a listener (call `attachPoolErrorHandler` on it). A query that is RUNNING when its backend is killed rejects with `57P01`; it does not reach the listener, so its caller's `catch` decides (request handlers and the cron jobs catch; see the report of this change for the exceptions). Tests: `dbPoolErrors.test.ts` (fake emitter: listener attached, no throw, redaction, rate limit with fake timers) and `dbPoolErrors.pg.test.ts` (real Postgres, skipped unless `MR_PG_TEST_URL` is set: kills idle backends and a running query, expects no uncaughtException and a working next query).

## Backend API
- GET /health and GET /api/v1/health — health check (same payload, both rate-limit exempt; the `/api/v1` prefix rewrite has a special case mapping it to `/health`; there is deliberately NO `/api/health`). Payload: `status, ready, timestamp, lastProbeAt, lastVantageOutageAt, lastAuditSyncAt, lastReviewsSyncAt, auditUpstream, auditUpstreamCheckedAt, auditCz` plus (additive, 2026-10-20) `sources`: `ownProbe{usedForScore:true,lastProbeAt}`, `cashuInfo{usedForScore:true,lastSyncAt,status}` (`auditCzSourceStatus()`: ok/partial/down/unknown), `reviews{usedForScore:false,lastSyncAt}`, `audit8333{usedForScore:false,lastSyncAt,status}` (legacy, display only); only timestamps, booleans and status words, no host or relay. `auditUpstream` (`ok|down|unknown`) is module-level in-memory state in `discovery.ts` set by `discoverMintsFromApi()` (last sync attempt, not a live check; `unknown` after restart until the next 6h sync); `/health` makes no outbound request. `getSyncTimesFromDb()` dedupes concurrent queries on cache expiry
- GET /api/mints/known — all mints with online status, latency, reliability score, degraded flag (snapshot fresh for 60 s, then stale-while-revalidate, see "Known-mints snapshot: stale-while-revalidate" below). **Website route since 2026-10-20:** no longer in the public-CORS list (a foreign `Origin` gets the JSON `403 cors_forbidden`; no-Origin and same-origin keep working) and no longer rate-limit exempt (on the read-only bucket, 150/min/IP, see "Rate limits"). Arithmetic: the site fetches it once per page load (`useKnownMints`: `staleTime` 5 min, `refetchOnMount`/`refetchOnWindowFocus` false, `retry: 2` only after a failure). Fields with no consumer in `src/` (candidates for later removal, kept for now): `auditNErrors`, `reviewWeightedRating`. Each mint carries `softwareLatest` (`{ major, minor }` of its own software family, `null` for unknown software — the ONE "latest" from `versionCatalog.ts` `getLatestVersionsMap()`, see docs/claude/scoring-and-probing.md); `/api/mints/version-history` still returns the same value as `latestGlobalVersion` (`nutshell/0.21`)
- **Wallet API v1 (2026-10-12, `backend/src/walletApi.ts`, contract in `docs/API.md` "API for wallets (v1)" and `docs/openapi/wallets-v1.yaml`):** `GET /api/wallets/mints` (list, filters `unit`, `minScore`, `includeOffline|Test|Archived|Unscored`, `nuts` (all listed NUTs advertised, strict `\d{1,3}` list of at most 32; `requiredNuts` of the same `filterWalletMints` that /recommend uses) and `eligible` (true/false on `eligibleForRecommendation`; added 2026-10-20), `limit` ≤ 200) and `GET /api/wallets/mints/<percent-encoded url>` (normalised with `normalizeUrl`, `isWellFormedMintUrl`, no DNS), reachable as `/api/v1/wallets/…` through the existing rewrite. A pure view of the `/api/mints/known` snapshot: `loadKnownMints()` in `index.ts` is the ONE computation (the snapshot of `knownMintsCache.ts`, stale-while-revalidate, with an in-flight promise, so one database read at a time for `/known`, the wallet API and `/api/mints/recommend` together; `invalidateKnownMints()` calls `invalidate()` of that cache). The mint object has exactly the keys of `WalletMint` (names fixed for v1: additive changes only; a contract test lists the key set and scans for IP/network/location/lastError/contact/review-text data; since 2026-10-20 the public NUT-06 `pubkey` and the boolean `hasOnion` are deliberately allowed). `methodology` comes from `shared/methodology.ts` (`METHODOLOGY_VERSION`, `METHODOLOGY_CHANGES`; bump both in the SAME commit as any formula change; since 2026-10-13 a byte-identical frontend copy `src/utils/methodology.ts` feeds the `/methodology` page, see `methodology-and-wallet-pages.md`; the mint object's field list `WALLET_MINT_FIELDS` lives in `shared/walletFields.ts` and a test compares it with the mapper). Errors of these routes: `{ error: { code, message, retryAfterSec? } }`; every other route keeps `{ error: "text" }`.
- **Wallet API additive fields (2026-10-20, task W2b; contract in `docs/API.md`, `docs/openapi/wallets-v1.yaml`, `WALLET_*` in `shared/walletFields.ts`):** no formula, weight, band, cap or `METHODOLOGY_VERSION` change. **Snapshot:** `computeKnownMints()` (still ONE query, 60 s) selects four more things from the wallet API's point of view only: `m.score_breakdown`, `m.keysets_checked_at`, `down_since` (a correlated subquery: `MIN(checked_at)` of failed `mint_history` rows after `COALESCE(m.last_online_at, '-infinity')`, evaluated only when the latest probe failed) and `keysets_json` (`json_agg` over `mint_keysets` rows with `last_seen_at >= keysets_checked_at - 10 minutes`, i.e. the keysets of the LATEST successful check: W2a stores the rows and stamps `keysets_checked_at` in two statements, so equality is not usable, and consecutive checks are about an hour apart). They (plus `probes24h` = the existing 24 h `total`) travel in `Snapshot.walletExtra` (a `Map` by URL, like `reviewFallback`; never serialised), so `/api/mints/known` keeps its exact key set. **Mint object:** every object has `downSince` (forced `null` unless the status is offline/degraded/archived), `hasOnion` (`=== true`), `authRequired` (`nutsLimits` keys `21`/`22`; "advertised", `protected_endpoints` is not parsed) and `auditNeutralReason` (`auditDataState()` from `shared/auditScore.ts`: `too-few` = `low_sample`, `too-old` = `stale`, `no-data` = `no_data`). `include=facts` adds `pubkey` (66-hex check), `firstSeenAt` (= `discoveredAt`), `lastOnlineAt` and `sample` (`probes24h`, `swaps7d`). **Why `facts` exists:** with all of them in the default list it grew 60.8% raw over the 2026-10-12 shape (57-mint synthetic fixture, `scratchpad` measurement in the W2b report); the task allows about 25%, so those four moved behind `include=facts` and the default grew 20.8%. The heavy fields (`facts` = `pubkey`+`firstSeenAt`+`lastOnlineAt`+`sample`, `keysets`+`keysetsCheckedAt`, `methods`, `scoreBreakdown`) are always built by `toWalletMint` (the `method` and `maxInputFeePpk` filters need them) and removed by `withIncludes()` unless `?include=` names them; the single-mint endpoint keeps all. `include` is part of the `WalletListFilter` and so of the memo key. **Filters:** `method` (bolt11|bolt12|onchain, case-insensitive, mint OR melt entry, with `unit` the entry's unit must match), `maxInputFeePpk` (0..1000000; the ACTIVE keysets in scope [unit, else all units] must be non-empty and ALL have a known fee <= limit: unknown fees and never-checked mints are excluded). `matchWalletMints()` returns every match, `filterWalletMints()` = it + `slice(limit)`; the list envelope adds `total`/`truncated`. **Single mint:** `findWalletMint()`: exact URL, else the ONE mint whose scheme+host+lower-cased path equals the request's; `canonicalUrl` is at the envelope level (null on an exact hit). **Score breakdown:** `backend/src/scoreBreakdown.ts` (`computeScoreBreakdown`, `readStoredBreakdown`); `prober.ts` writes it into `mints.score_breakdown JSONB` (nullable, additive migration, NULL until the next probe cycle) in the SAME `UPDATE` as `last_reliability_score` with the SAME `now`, so it can never disagree with the stored score and is never recomputed at read time; `readStoredBreakdown` rejects a malformed value (`null`). Details of the parts and the .5 rule: `scoring-and-probing.md`. **Tests:** `integration/wallet-api-w2b.test.ts`, `scoreBreakdown.test.ts`, `prober-audit-inputs.test.ts`, `dbKeysetsMigration.test.ts`, and `walletApi.pg.test.ts` (real Postgres via `MR_PG_TEST_URL`, run it ALONE: parallel `initDb()` calls from two pg test files race on `CREATE TABLE`).

Before this it ran its own SQL and listed test mints and brand-new mints. - **CORS (middleware in `index.ts`, after the `/api/v1` rewrite):** `Access-Control-Allow-Origin: *` (GET, HEAD, OPTIONS, no credentials, exposed headers ETag, Retry-After, X-RateLimit-*, and since 2026-10-20 Deprecation, Sunset, Link: one constant `PUBLIC_CORS_EXPOSE_HEADERS`, so /health lists them too) ONLY for `/api/wallets/*`, `/api/mints/recommend` and `/health` (`isPublicCorsPath`; `/api/mints/known` was removed from the list on 2026-10-20); preflight = 204 before the rate limiter. Every other route keeps the `ALLOWED_ORIGINS` list, and a foreign `Origin` there is a JSON `403 { error: { code: "cors_forbidden" } }` (it used to be Express's HTML 500). Adding a route to the public list is a security decision: read-only, cacheable, no personal data.
- **Caching (`sendCachedBody`):** `/api/mints/known`, `/api/wallets/*` and `/api/mints/recommend` send `Cache-Control: public, max-age=300` and a strong ETag (sha256 of the body, memoised per snapshot) on every response, hit or miss; `If-None-Match` → 304. `generatedAt` is the snapshot time, not `now`, so the ETag stays stable within a snapshot. Since 2026-10-13 the shared-data website routes `/api/stats`, `/api/stats/reliability-movers`, `/api/mints/swaps`, `/api/mints/audit-cz` and `/api/mints/nostr-reviews` use it too with their OWN max-age (60 s / 600 s / 300 s / 60 s / 120 s; `sendCachedBody(res, body, maxAgeSec)`, `cachedBodyOf(data)` memoises the body of the stats caches per data object) instead of `max-age=N` + Express's weak ETag. NOT shared: submit, probe, notifications; `/api/og/mint` (HTML for bots) still has its own `max-age` without `public`.
- **Unmatched `/api/*` (2026-10-20):** a final `app.use('/api', …)` at the end of `index.ts` answers a JSON 404 instead of Express's HTML "Cannot GET": `/api/v1/*` (judged by `req.originalUrl`, since the rewrite already ran) uses `sendWalletError(res, 404, 'not_found', …)`, every other path `{ error: 'Not found' }`. nginx `location /api/` forwards every unknown path to Express, nothing is swallowed by the SPA fallback.
- **Known-mints snapshot: stale-while-revalidate (2026-10-22, task D3d; `backend/src/knownMintsCache.ts`, wired in `index.ts` as `knownMints` / `loadKnownMints()`).** **Why:** the computation of the snapshot took about 3.3 to 3.9 s and the visitor must not be the one who waits. (Correction, task E2/E2b, 2026-10-22: this was first read as a cold-cache cost of the 7-day aggregate over `mint_history`. It was JIT compilation of the large query, see "Database JIT is off" below; the snapshot is still served stale-while-revalidate.) **Rule:** (1) younger than `KNOWN_MINTS_CACHE_TTL` (60 s): returned as is; (2) older than the TTL but younger than `KNOWN_MINTS_STALE_LIMIT` (5 min, same as `STATS_STALE_LIMIT`; was 10 min until 2026-10-22, task E1): the old snapshot is returned at once and ONE background refresh starts (single-flight: concurrent requests join it, never a second one); (3) older than the stale limit or no snapshot: the request computes synchronously (single-flight shared) and an error surfaces as before (500). **Failure:** a failed background refresh keeps the snapshot (served until the stale limit) and logs one line `[known-mints] background refresh failed: <ErrorName> (<code>)` at most every 5 min, never the message (it can carry a connection string). **Timer:** `knownMints.start()` runs a fire-and-forget refresh and then one every `KNOWN_MINTS_REFRESH_INTERVAL` (45 s, below the TTL, `unref`'ed, skipped while a refresh runs), so under a running server the snapshot normally never expires. **Warm-up:** `start()` is called in the start-up chain after `initDb()` and the seed (next to `startCron()`), so `app.listen`, `initDb`, seed and cron keep their order and nothing waits for it; a failed warm-up is only logged. **Invalidation:** `invalidateKnownMints()` (after a submit) drops the snapshot AND the in-flight promise and bumps a generation counter; a computation that started before it does not store its (older) result, so the next request computes fresh data (never the stale snapshot) and a late old refresh cannot overwrite it. **HTTP unchanged:** `max-age=300`, ETag (hash of the body, so it changes only when the content changes), memoised body, response shape. **Not covered:** the trend and movers caches still use the plain TTL pattern (first request after expiry waits); `/api/stats` moved to the same holder in task D3f (next entry). Tests: `__tests__/knownMintsCache.test.ts` (fake timers, mocked compute).
- **`/api/stats`: stale-while-revalidate (2026-10-22, task D3f; `backend/src/statsCache.ts`, wired in `index.ts` as `stats` / `computeStats()`).** Same holder (`createSwrCache`) and same rule as the known-mints snapshot, with its own named constants: `STATS_CACHE_TTL` 60 s (also the response `max-age`, unchanged), `STATS_STALE_LIMIT` 5 min, `STATS_REFRESH_INTERVAL` 45 s. Fresh: served as is; older than the TTL but younger than the stale limit: old payload at once + ONE background refresh (single-flight); older or no snapshot: synchronous compute, an error is a 500 as before. - **"More alerts" DMs (2026-10-10; cooldown, hysteresis and daily cap 2026-10-12)** — `notifyAlert(mintUrl, kind)` / `recordAlertClear()` in `nostrService.ts`, decisions in `alertTriggers.ts` (`Condition` = active / clear / unknown), all limits as named constants in `notificationLimits.ts`, wired from `probeMintToDb` (`prober.ts`: active -> `notifyAlert`, clear -> `recordAlertClear`, unknown -> nothing). Flags `notify_on_mint_melt_issues` / `notify_on_version_outdated` / `notify_on_nut_loss` default false (opt-in per type, unchanged). **What triggers:** mint/melt = audit_cz 7-day aggregate (`audit_cz_total`/`audit_cz_blamed`), active at blamed/total >= 50 % with >= 10 swaps and an aggregate fetched within 3 days (older/too small = unknown); version = `classifyMintVersion` label `outdated` (>= 2 minors behind, grace applied) on a successful probe; NUT loss = edge in the probe, stored `nuts_limits` vs the new `/v1/info` (NUT-04 or NUT-05 supported before, not now; `disabled: true` counts as lost; "restored" = both supported again). Both the version string and the nuts come from the mint, so they can flap on every probe.
  - **Claim (atomic, one statement):** `last_notified_*_at` is the time of the subscriber's LAST claim and is **never reset to NULL by a cleared condition** (the old reset bypassed every cooldown: a flapping mint gave a DM every second probe, about 6,700 DMs per day for one subscriber on 20 flapping mints; 9,600 with mint/melt). A subscriber can be claimed when the slot is NULL (never notified), or when the cooldown has passed since the last claim (**mint/melt 12 h, version and NUT loss 24 h**, `ALERT_COOLDOWN_HOURS`) AND the mint has been **re-armed** since that claim (`mints.alert_rearmed_<kind>_at` > the claim). The claim is a CTE with `FOR UPDATE OF ns` + `UPDATE ... RETURNING prev_at`, so two probes or two backend processes cannot both send; a failed send puts the claim back to `prev_at` (guarded on the claimed time) and gives the cap slot back. Claim times are cut to milliseconds (`date_trunc('milliseconds', now())`), also for Goes down/up: they are read back as a JS `Date` and used as the release guard, and PostgreSQL's microseconds never compared equal (before 2026-10-12 a failed send was never released).
  - **Hysteresis:** `notifyAlert` (condition active) sets `mints.alert_clear_streak_<kind>` to 0; `recordAlertClear` (condition clear) adds 1 and, when the streak reaches `CLEAR_PROBES_TO_REARM` (12 consecutive clear probes, about 1 hour), sets `alert_rearmed_<kind>_at = now()`. Once the streak is full nothing is written any more. `unknown` neither resets nor counts. Stored per mint, so it survives a restart. Net effect: one DM per episode and subscriber, never more often than the cooldown; a condition that returns after 11 clear probes does not re-arm; one that returns after 12 does but still waits for the cooldown (then a single delayed DM goes out if it is still active). **Change of behaviour:** mint/melt used to repeat every 12 h while the ratio stayed above 50 %; it is now one DM per episode like the other two.
  - **Daily cap per subscriber (all five types, `dmQuota.ts`, table `notification_dm_quota`):** at most `DM_DAILY_CAP` = 40 notification DMs per pubkey per window; the window starts with the first DM and lasts `DM_CAP_WINDOW_HOURS` = 24 h, the first DM after it starts a new window (count back to 1). `reserveDmSlot` is ONE atomic upsert with `LEAST(count + 1, cap + 1)`, so the counter stays bounded however many DMs are due. Only DMs that were really claimed count; the 41st and later are **dropped, not queued** (their claim stays used), and the first over-cap DM of a window triggers exactly ONE summary DM (`DM_CAP_SUMMARY_TEXT`, not counted; flag `summary_sent`, flipped atomically; freed again if the summary cannot be published). Worst case per subscriber per window: 40 + 1 = 41 DMs (the windows are fixed from the first DM, so across a window boundary up to 82 can fall into one sliding 24 h). Rows older than 2 days are pruned with the 30-day subscription pruning (`pruneOldNotificationSubscriptions`).
  - **Subscriber relays (2026-10-12):** `POST /api/notifications/subscribe` accepts 1-10 relays, each `wss://` on port 443 or `ws://` on port 80 (no port = the default; `isAllowedRelayPort` in `ssrf.ts`, checked first inside `checkWsUrlSafety`, so another port gets the usual `blocked` -> 400 "relays must be an array of 1-10 valid ws:// or wss:// URLs" without any DNS lookup), plus all the earlier checks (private/internal address blocking, DNS-rebinding pin at connect, <= 500 chars, 25 distinct relays and 50 subscriptions per pubkey). The 13 fixed `NOTIFICATION_RELAYS` are unaffected. Rows stored before the rule are NOT deleted: at send time `targetRelaysFor` skips stored relays on other ports and the run's log line gets a counts-only `, N stored relay(s) skipped (port not 80/443)`. The browser (`resolveNotificationRelays`, `notificationSubscription.ts`) leaves such relays out of the NIP-65 list it sends (one bad relay would make the server reject the whole request) and falls back to the fixed list when none is left.
  - Texts (2026-10-12, `buildDmText` in `nostrService.ts`, same shape as Goes down/up): every DM of every type is a fixed template + the hostname (`dmHostname`: only if `isWellFormedMintUrl` accepts the URL, else the fixed `A watched mint`) + `View details: https://mintradar.org/mint/<encodeURIComponent(mint url)>`; e.g. `⚠️ {host}: mint or melt issues were detected.`, `ℹ️ {host} is now running outdated software.`, `⚠️ {host} no longer supports NUT-04 or NUT-05 (minting or melting).`. The mint's name, version, MOTD, error texts and the raw URL (path/query) are mint-controlled and NEVER used in a DM (`dmMintName` was removed; `notifyAlert` no longer reads `mints.name`); the only `://` in a DM is the one of `https://mintradar.org/`. Tests: `src/__tests__/dmText.test.ts` (hostile table + template snapshots), `nostrService.test.ts` (SQL shape, cap, release). The state machine was also run on a throwaway PostgreSQL with a fake clock (shifted timestamps): 48 h of a flapping version or NUT flag = 1 DM, 100 mints down = 40 + 1 summary, 20 flapping mints with all five types on = 41 DMs per 24 h (was 9,600). Existing `notifySubscribers` keeps its 60-minute per-direction cooldown.
- **`NOTIFICATION_SERVICE_NSEC` IS set and active in production** (verified 2026-09-07: container env has it, backend logs `[notify-service] service identity loaded (pubkey d03c080f…)` + publishes the "MintRadar Alerts" kind:0). Replaced with a single conditional `UPDATE notification_subscriptions SET last_notified_<dir>_at = now() WHERE mint_url = $1 AND notify_on_<dir> = true AND (last_notified_<dir>_at IS NULL OR last_notified_<dir>_at < now() - INTERVAL '<COOLDOWN_MINUTES> minutes') RETURNING pubkey, relays, …` that **claims** the slot in the DB — DMs go only to the rows it returns, the loser of a race gets zero rows. A claim whose DM never goes out (all relays failed / `wrapEvent` threw) is released (`last_notified_<dir>_at` → NULL, guarded on the exact timestamp set so a concurrent successful claim is never clobbered) so the next cycle retries. `COOLDOWN_MS` (JS) → `COOLDOWN_MINUTES` (one source, used in the SQL interval).

## Network layer: SSRF rules, relay connections, icon proxy (2026-10-14)

**Rule: every outbound connection to a host that is not hard-coded goes through the safe wrappers in `backend/src/ssrf.ts`.** HTTPS: `safeFetch` (validates the URL and every redirect hop, connects through `safeLookup`, one deadline, no credentials) and `readBodyLimited` / `readJsonLimited` (size caps). Relay sockets that are not hard-coded: `DnsPinnedWebSocket` (nostrService.ts, `lookup: safeLookup`). Subscriber-supplied relay URLs are checked once with `checkWsUrlSafety` on subscribe and again at connect time by the pin. Known exceptions, deliberately: the hard-coded relay lists (`DISCOVERY_RELAYS`, `REVIEW_SYNC_RELAYS`, ...) used by discovery.ts (root `SimplePool`) and reviewsRelayFetch.ts do not go through the DNS pin; a dynamic list there must be switched to the pinned socket first.

| Rule (ssrf.ts) | What it does |
|---|---|
| Scheme allow-list | `checkUrlSafety`: `https:` only; `checkWsUrlSafety`: `ws:` / `wss:` only; everything else (`http`, `file`, `ftp`, `gopher`, `data`, `javascript`, `blob`, scheme-relative, empty) → `blocked` before any lookup |
| URL length | over 500 characters → `blocked` |
| Port | relays: `wss` only on 443, `ws` only on 80 (`isAllowedRelayPort`, before DNS); mints: any valid port on a public host (mints run on 3338, 8085, ...), an invalid port → `blocked` |
| Address ranges | `isBlockedIpString` / `isBlockedAddress`: loopback, private, link-local (incl. 169.254.169.254), unique-local, unspecified, reserved (TEST-NETs, benchmarking 198.18/15, 192.0.0/24, 240/4), CGNAT 100.64/10, broadcast, **multicast, discard 100::/64, benchmarking 2001:2::/48, site-local fec0::/10** (the last four since 2026-10-14) |
| IPv4 inside IPv6 | unwrapped and re-checked: IPv4-mapped, NAT64 64:ff9b::/96, 6to4, Teredo (XOR), IPv4-translated ::ffff:0:0:0/96; never public at all: IPv4-compatible `::/96` (`https://[::127.0.0.1]` is printed by the URL parser as `[::7f00:1]`) and RFC 8215 `64:ff9b:1::/48` |
| IP-literal notations | the WHATWG URL parser folds decimal / hex / octal / short forms and unicode dots into dotted quads before the check, so the host that is checked is the host the socket uses; tests compare `new URL(x).hostname` |
| DNS policy | public answers only → `safe`; any blocked or unparseable address in the set → `blocked`; resolver error or empty answer → `dns-error` (not an SSRF signal, never `safe`); nothing is cached |
| DNS time limit (2026-10-16) | a resolver that never answers is cut off: `DNS_LOOKUP_CEILING_MS = 3_000` (`ssrf.ts`) is the most the DNS step of ONE request may take, all its lookups together (a redirect hop's lookup gets what the earlier ones left, not a fresh 3 s). **One deadline:** `safeFetch` passes a `DnsBudget` (`deadlineAt` = start + `timeoutMs`, `dnsUsedMs`) to every `checkUrlSafety`, so DNS time counts against the SAME `timeoutMs` as the fetch (DNS 2 s + hanging fetch → aborted at 5 s total, not 7 s); each lookup gets `min(time left to the deadline, 3 s - DNS time already used)`, nothing left → `dns-error` without asking the resolver. A standalone `checkUrlSafety` / `checkWsUrlSafety` gets the ceiling only. **Fail closed:** a timeout is the ordinary `dns-error` outcome (no new `UrlSafetyResult`, `onRejected` still says `'dns-error'`, the probe records the mint offline with 'DNS resolution failed', relay validation stores the relay like any dns-error relay, `isSafeUrl` is false); it is told apart only by the log line `[ssrf] dns-timeout` (no host name) and is never cached. The timer is cleared on every path and the abandoned lookup has a `.catch`, so a late answer or rejection cannot become an `unhandledRejection`. The connect-time pin (`safeLookup`, used by undici and `DnsPinnedWebSocket`) has the same 3 s bound (error `code: 'ETIMEOUT'`, late answer dropped). Not covered, deliberately: `resolve4` in `mintAddress.ts` and the geo lookup in `prober.ts` are display-only, not SSRF checks |
| Rebinding | validation resolves once (`dns/promises`), the connection resolves through `safeLookup`, which re-checks the very answer the socket then uses; nothing resolves a third time |
| Redirects | followed by hand, max 3 hops, every hop re-validated (`checkUrlSafety`), relative `Location` resolved against the current URL, a missing / unparseable `Location` → `bad-redirect` |
| Limits | one `AbortSignal.timeout` for the whole call (not per hop); caps in `RESPONSE_CAPS`, `Content-Length` pre-check plus counting while streaming; honest `User-Agent: MintRadar/1.0 (+https://mintradar.org)` |

Tests (no real network, no real DNS; lookups and undici are stubbed, the one real socket is a stub server on 127.0.0.1 that must stay untouched): `backend/src/__tests__/ssrfAddresses.test.ts` (ranges, IPv6 embeddings, URL notations, parser differentials), `ssrfDns.test.ts` (schemes, ports, host forms, DNS policy, `safeLookup`, rebinding), `ssrfFetch.test.ts` (redirects, deadline, body limits), `ssrfDnsTimeout.test.ts` (DNS ceiling, shared deadline, no dangling timers / unhandledRejection, pinned path; fake timers), `ssrfCorpus.test.ts` (every configured relay and a sample of real mints must stay allowed), plus the older `ssrfGuard.test.ts`. **To add a case:** put one row in the matching table (`V4` / `V6` in ssrfAddresses, `NOTATIONS`, the `BAD` lists in ssrfDns) with the expected verdict; for a new rule change `ssrf.ts` and add a row that fails without it. A new relay or mint host that the guard wrongly blocks shows up in `ssrfCorpus.test.ts`. Coverage of `ssrf.ts`: 100 % lines, 99 % branches (`npx vitest run --coverage --coverage.include=src/ssrf.ts`).

**Relay connections: never leave a promise or an error event floating.** nostr-tools closes a socket that is still CONNECTING when its connection timeout (3 s) fires and nulls `onerror` straight away; `ws` then emits `error` with no listener and Node raised `uncaughtException: WebSocket was closed before the connection was established` once per start (discovery at +10 s, the service profile at start). Fixed at the source: every nostr-tools pool connects with `RelayWebSocket` (`wsPolyfill.ts`, a `ws` subclass with a permanent no-op `error` listener; `DnsPinnedWebSocket` extends it). The process-level `uncaughtException` / `unhandledRejection` handlers in `index.ts` stay as a last resort for unexpected errors and only log; they are not what handles this case (and, since 2026-10-14, they are registered in the not-under-test start block, next to SIGTERM/SIGINT, not at import). Rules for relay code: attach `error` / `close` listeners before the socket is used; bound every connection with a timeout; `Promise.allSettled` over several relays; give a floating `publish()` promise a `.catch`; close in `finally` (`pool.destroy()`, `conn.close()`). `relayConnectionErrors.test.ts` runs the four call sites (`publishToRelays`, the attestation pool publisher, the root `SimplePool` of discovery.ts, `connectRelayWs`) against a stub relay that refuses, accepts and stays silent, closes at once, sends a close frame or invalid frames, and asserts no uncaught exception, no unhandled rejection (listened for 200 ms after the call), a bounded duration and no socket left. Separate nostr-tools problem, not reachable here: with Node's NATIVE WebSocket a failed connection recurses (`RangeError: Maximum call stack size exceeded`, onerror -> close -> error); the backend uses `ws` for that reason, standalone scripts must set `useWebSocketImplementation(ws)` too. nostr-tools 2.25.2 (latest on 2026-10-14) still has both.

**Icon proxy (`GET /api/mint/icon`, mintIcon.ts): why a mint gets no icon (204).** Since 2026-10-20 an icon that cannot be served answers **`204 No Content`**, no body, `Cache-Control: public, max-age=1800` (the same as the former 404), from one helper (`sendNoIcon` in `index.ts`). It was a 404, and Chromium prints `Failed to load resource: … 404` in the console for every such `<img>` request on every page load. **One answer for every reason** (unknown mint, no or non-https `icon_url`, blocked address, DNS, TLS, upstream status, over 512 KiB, wrong type or SVG, empty body, timeout, an internal error): the route must not tell a caller why an icon failed (no oracle for SSRF probing of the mint's icon host); `mint-icon.test.ts` asserts identical status, body and headers across all of them, and that an SSRF-blocked icon host answers exactly like a mint without an icon. A servable icon is unchanged (200, image type, `CSP: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `nosniff`) except for its caching (Task P2 part 3, 2026-10-21): `Cache-Control: public, max-age=604800` (7 days; was 86400) and a strong `ETag` = sha256 of the bytes, first 32 hex (`iconEtag()` in `mintIcon.ts`, computed once per cached icon); a request whose `If-None-Match` matches (Express `req.fresh`) gets a bodyless `304` with the same ETag, Cache-Control, CSP and CORP headers and no Content-Type. The 204 keeps `max-age=1800` and never has an ETag. Consequence: a browser keeps an icon up to 7 days without asking, so a mint that changes its icon shows the new one after at most that long (the server cache is 6 h). Tests: `integration/mint-icon.test.ts` ("ETag and conditional requests"), `mintIcon.test.ts` (`iconEtag`). The 512 KiB limit, the content-type allow-list (no SVG), the SSRF guard and the 6 h / 24 h in-process cache did not change. A missing or over-long `url` query is still `400`.

Measured in Chromium 156 (Playwright, a local server answering `/icon-204`, `/icon-404`, `/icon-ok` for three `<img>` elements): 204 → `error` event, **no console message**; 404 → `error` event plus `Failed to load resource … 404`; 200 PNG → `load`, no message. So the monogram still appears (`MintFavicon` `onError`) and the failure is remembered 24 h by `mintIconFailureCache` (no retry loop). The service worker needs no change: `/api/` is `NetworkOnly`, a 204 is never cached by it.

Chain: `index.ts` route -> `getMintIcon` (cache 6 h / 24 h negative) -> `mints.icon_url` (https only) -> `safeFetch` (5 s) -> 2xx -> `readBodyLimited` (512 KB) -> Content-Type allow-list or magic-byte sniff (raster only, no SVG). The frontend treats `iconUrl` only as a "has icon" hint and drops to the monogram on `<img onerror>`. ## Backend unit tests: no wall-clock budget on CPU work (2026-10-20)

A test must not depend on how fast the machine is. `healthPublisher.test.ts` "publishes at most 200 events per run" signed 260 events with real BIP-340 (~1.4 s idle) against vitest's 5 s default timeout; it passed in 15 of 15 idle runs and failed in 6 of 6 runs with 2x CPU oversubscription (a busy laptop, a CI neighbour). Rule: if a test asserts counts or planning and not signatures, replace the CPU-heavy step in that test only (a flag-switched wrapper around the real function via `vi.mock(..., importOriginal)`, reset in `beforeEach`), keep real crypto in the tests that verify it, and never "fix" it with a longer timeout, `retry` or `skip`. Check a suspected flaky test by running the suite repeatedly with burner processes at 2x `nproc` (the JSON reporter keeps failing titles per run).


## Mint change log (2026-10-20, task W4)

Confirmed changes in a mint's PUBLIC data, recorded as facts with a source and a time (measurement station, not arbiter: no score input, no `METHODOLOGY_VERSION` bump, no verdict words). Code: `backend/src/mintChanges.ts`. Contract: wallet API `changes` / `changedSince` (`docs/API.md`, OpenAPI, `walletFields.ts`), tag `mint_last_change` (`nostr-health-assertions.md`), the Mint Detail "Change log" panel (`card-and-mint-detail-ui.md`), two DM types (below).

**Tables** (`db.ts`, additive and idempotent): `mint_changes` (`id BIGSERIAL`, `url` FK `ON DELETE CASCADE`, `change_type`, `field`, `old_value`, `new_value`, `observed_at`, `first_seen_at`, `source` CHECK `info|keysets`; index `(url, observed_at DESC)`), `mint_change_state` (`url` PK FK cascade, `info JSONB` and `keysets JSONB` = the last CONFIRMED normalised values = the baseline, `tracking_since`, `updated_at`) and `notification_subscriptions.last_notified_change_id BIGINT` (DM dedupe). Retention 365 days: `pruneOldMintChanges()` (`MINT_CHANGES_RETENTION_DAYS`) runs in the 03:00 daily prune job of `cron.ts`, in the same try block as `pruneOldHistory()`.

**Where it is fed (no extra request to a mint):** `probeMintToDb` calls `recordInfoObservation(url, raw)` right after the successful `/v1/info` has been stored (the 502/503/504 retry branch stores nothing and observes nothing); `collectMintKeysets` calls `deps.onObserved` (default `recordKeysetsObservation`) after a successful `store`. Both wrappers never throw. A failed fetch, a non-2xx, an invalid body, a failed store, an empty keysets list, or a partly malformed/truncated one (`skipped` or `ignored` > 0) never reaches them, so nothing is compared and the stored baseline is never overwritten.

**Rules.** *Baseline:* the first observation of a mint, or of a field that was never stored, is a baseline (the state is written, no change row), so a deploy cannot create a burst. *Confirmation:* a difference becomes a change only when two CONSECUTIVE successful observations agree (`stepValue`; in-memory `pending` map, lost on restart: that can only delay a change; a flip back or a third value starts over). `/v1/info` fields are confirmed per field (two probes, 5 minutes apart), the keysets as one whole signature (two hourly checks). *Missing fields:* a field absent from a partial answer is absent from the snapshot, never an empty value, so it cannot compare or overwrite. *Legacy shapes:* `normalizeStoredInfo` / `normalizeStoredKeysets` bring whatever is stored (arrays, unsorted lists, padded text, upper-case key, the wallet API's field names) to the normalised form before comparing, so comparison is always normalised-to-normalised.

**Types and normalisation as implemented.** `pubkey_changed` (field `pubkey`: `normalizeMintPubkey`, the full 66-hex key), `motd_changed` (`motd`), `name_changed` (`name`), `description_changed` (`description` and `description_long`, two fields, one type), `contact_changed` (`contact`: ONLY the method kinds, sorted and de-duplicated, and the entry count, `"email, nostr (2)"`, `"none"`; never a contact value), `version_changed` (`version`: as reported, whitespace collapsed, control characters removed, 100 characters), `nuts_changed` (`nuts`: numeric NUT keys sorted ascending, `"4, 5, 7"`), `methods_changed` (`methods`: `mint:<method>/<unit>` for NUT-04 and `melt:...` for NUT-05, lower-case, sorted, `"none"`), and from the keysets: `keyset_added`, `keyset_removed`, `keyset_deactivated`, `keyset_reactivated`, `keyset_final_expiry_changed` (compared BY ID; the snapshot per keyset is id, unit, active, fee ppk, final_expiry as UNIX seconds, shown as ISO), `input_fee_changed` (field `input_fee`: the largest `input_fee_ppk` among the ACTIVE keysets per unit, fees compared as numbers, old and new written as `"sat: 100 ppk, usd: 0 ppk"` or `"none"`). Text fields (motd, name, description) are plain text: whitespace collapsed, control and bidi/zero-width characters removed, every URL (`scheme://`, `www.`, `mailto:`/`nostr:`/`lightning:`/... and a host with a path) replaced by `[link]`, at most 200 characters (by code point). Field order in the JSON and list order never matter.

**Noise control.** At most 20 rows per mint and UTC day (`MAX_CHANGES_PER_MINT_PER_DAY`, `decideStorage`); every further change of that day is merged into ONE row per change type with `old_value` NULL and `new_value` `"multiple changes"` (later ones only touch its `observed_at`; no counter). The merged row is a summary: it never sends a DM. A commit (state + rows) is one transaction (`commitChanges`), so a crash cannot store a change without its baseline.

**Read side.** `GET /api/mints/changes?url=` (website route: default CORS allow-list and the read-only 150/min/IP limiter like `/api/mints/known`; `400` bad url, `404` untracked mint, `public, max-age=60` + ETag) returns `{ url, trackingSince, changes }` with the newest 100 (`ROUTE_CHANGES_MAX`). The wallet API reads the newest 50 per mint in the SAME snapshot query (a `json_agg` sub-select `changes_json`, so the snapshot is still one read), `WalletMint.changes`, `include=changes` (10 per mint on the list), `changedSince` (`parseChangedSince`: ISO 8601 with Z/offset, a bare date, or UNIX seconds of 9-11 digits; else 400). The default list has no `changes` key (`mint-changes-api.test.ts` pins it).

**DMs (two new types, `nostrService.ts` `notifyMintChanges`).** Only a confirmed `pubkey_changed` and a confirmed `input_fee_changed` (never MOTD, description, version, keysets, merged rows, baselines). Recipients: every ACTIVE subscriber of the mint (at least one of the five notification flags on; there is no separate pill for these). Dedupe: an atomic claim `last_notified_change_id < newest id of the run` (`FOR UPDATE` + re-check like `notifyAlert`; the claim is given back when nothing was delivered), the daily cap and the sending path are the existing `deliverDm`. One DM for everything confirmed in the same run. Text: `CHANGE_DM_SENTENCES` / `buildChangeDmText`: `Mint <hostname> changed its public key on <YYYY-MM-DD HH:MM UTC>.` and `Mint <hostname> changed its input fee on <time>: <old> -> <new> ppk (<unit>).` + `View details: <MintRadar mint page>`. The text uses the HOSTNAME, not the mint's name (a mint-controlled string never enters a DM signed by the service key; same rule as the older templates), and a unit outside `sat/msat/usd/eur/btc` is written `other`. No verdict word, no advice. The change is detected in memory and the DM sent right after the commit: a restart between the two loses that DM (at-most-once), it never sends one twice.

**NUTs rule stamp (2026-10-21, methodology 4):** `nutKeys()` lists only declared, not `supported:false` NUTs (`isNutDeclaredSupported`). `mint_change_state.nuts_rules INTEGER NOT NULL DEFAULT 0` holds the rule version the stored `info.nuts` was built with (`NUTS_RULES_VERSION` = 1). `observeInfo` replaces the nuts baseline silently (no change row, no pending, stamp set in the same commit) on the first successful observation that has a `nuts` object when the stamp is older; afterwards a change needs the usual two agreeing observations, and a NUT flipping to `supported:false` is a `nuts_changed`. Tests: `mintChangesNutRules.test.ts`, `mintChanges.pg.test.ts`.

**Tests.** `mintChanges.test.ts` (sanitising, normalisation, baseline / one observation / two / reorder / partial / each type / legacy shapes / cap decision / what may become a DM), `mintChangesHooks.test.ts` (probe and keysets hooks: failures never reach the log), `mintChangeDm.test.ts` (wording, combined DM, claim, release, no-DM cases), `dbMintChangesMigration.test.ts`, `mintChanges.pg.test.ts` (real Postgres via `MR_PG_TEST_URL`: table, FK cascade and rollback, per-day cap, index use, retention, the snapshot sub-select), `integration/mint-changes-api.test.ts`, `walletApi.pg.test.ts` (changes from the real snapshot SQL). Mutation proofs of the task: no confirmation, compare after a failed fetch, a URL in a MOTD, a contact value stored, a change triggering `publishReason`, a DM for a MOTD change, `changes` in the default list: each made a named test fail (reverted).

## Contact checks (2026-10-20, task W6a)
Facts about the contact entries a mint lists in `/v1/info` (`backend/src/contactChecks.ts`): per entry `{ kind, formatValid, domainResolves, checkedAt }`. A measurement station: no score change, no `METHODOLOGY_VERSION` bump (the Contact row still means "the mint lists a contact", 5 points), no verdict words.

- **Where.** The successful `/v1/info` body the probe already fetched (`prober.ts`, right after `recordInfoObservation`): no extra request to a mint. `queueContactChecks()` is **not awaited**, never throws and never rejects; DNS work runs in the background, so a lookup, a DNS exception or a failed store cannot change the probe result, the stored score and breakdown, the status or a notification (`contactChecksProbe.test.ts` compares the recorded writes with the checks switched off, with DNS rejecting, DNS throwing and the store failing). The stored column is read with the existing `SELECT version, pubkey, nuts_limits, contact_checks` of the probe (no extra query).
- **Stored.** `mints.contact_checks JSONB` (nullable, no default, metadata-only migration): an array of the four fields per entry plus `rules` (the `CONTACT_RULES_VERSION` the result was computed with; stored only, `readStoredContactChecks` drops it, so no API answer carries it), never a value, a local part or a domain. `NULL` until the first check; `[]` when the entries are gone. Re-checked at most once per 24 h per mint (`isCheckDue`: the oldest `checkedAt`), earlier only when the sorted list of kinds changed **or a stored entry has another `rules` value than `CONTACT_RULES_VERSION`** (see "Rules version" below). One check per mint at a time (`running` set).
- **Kinds.** `email, nostr, twitter, x, telegram, signal, url, other`: the stated method lower-cased; `website`/`url` are `url`; anything else (`vk`, `matrix`, ...) is `other`, so a mint cannot put its own text into the stored kind. At most 10 entries are read and at most 3 `email` entries are checked.
- **Checks.** email: dot-atom syntax (local part 64, whole 254, internationalised names converted with `domainToASCII`), IP literals valid syntax with no lookup; nostr (`parseNostrContact`, 2026-10-20 Part N): after trimming whitespace and removing an optional `nostr:` prefix (any case) an `npub` or `nprofile` with a valid bech32 checksum and a 32-byte pubkey (all lower or all upper case; **mixed case is rejected**, BIP-173), 64 hex, or a NIP-05 style `local@domain` (local `a-z0-9._-` case-insensitive, domain a public name, bare host only), nothing else; no relay is asked and **no HTTP request** goes to `/.well-known/nostr.json`; url: `https` + public host name, **no fetch and no DNS**; every other kind: printable text, 1-200 characters. `domainResolves` is only ever set for an e-mail, or a NIP-05 style nostr name, with a recognised format whose domain is a normal public name (`isPublicDomainName`: no IP, `localhost`, single label, numeric or reserved TLD such as `.local .internal .lan .test .onion .arpa`, `example.com/net/org`): MX records (an RFC 7505 null MX is `false`), else A/AAAA (implicit MX) = `true`; `ENOTFOUND`/`ENODATA` everywhere = `false`; **a timeout, SERVFAIL, refused, a throwing resolver or the 9 s deadline = `null` (unknown), never `false`**.
- **DNS.** `dns/promises` `Resolver({ timeout: DNS_TIMEOUT_MS = 2000, tries: 1 })`, the system resolver, a query for the name only; **one immediate retry (task E1, 2026-10-22)** when the first attempt ends unknown (timeout, SERVFAIL, throwing resolver), inside the same `DNS_TOTAL_MS` = 9 s deadline (Task G3: an attempt is at most two queries in a row, MX then A/AAAA, so two attempts cost at most 4 x 2 s = 8 s and the second attempt can no longer be cut off; with the old 3 s per query the worst case was 12 s; a test pins 4 x `DNS_TIMEOUT_MS` < `DNS_TOTAL_MS`), never after a definite `true`/`false` (NXDOMAIN/ENODATA/null MX); global concurrency 5, queue bounded at 500 (beyond that a domain stays `null`); answers cached **per domain for 7 days in memory** (only `true`/`false`; `null` is never cached; 500 domains at most; simultaneous questions about one domain share one lookup). Nothing connects to a contact domain. **Carry-forward (Task G3, `keepKnownTrue`):** a lookup that could not tell (`null`) does not overwrite a stored `true` of the same position and kind for up to 24 h after that answer; the entry keeps the OLD `checkedAt` (so the window cannot restart with every failed check and the next probe tries again); a real `false` always overwrites, after 24 h the `null` stands, an entry of another rules version is not carried. No new column: it only reads what is stored. **Caveat:** the normal re-check cadence is also 24 h, so the carry-forward only fires on an early re-check (the entry kinds changed); a grace longer than the cadence would be needed for the regular case (open decision).
- **Privacy.** No log line carries a value, a domain or an error text (the failure line is fixed: `[contact-checks] check or store failed`); the canary tests (`contactChecks.test.ts`, `contactChecks.pg.test.ts` dumping every table) prove it for writes, logs and errors. See also `third-party-requests.md` (the server asks DNS for the domain of an e-mail contact).
- **Exposed.** The on-demand probe `GET /api/mint/probe` answers `contactChecks` for a **known** mint (`[]` when none; the unknown-URL answer is unchanged), which is what Mint Detail reads; `/api/mints/known` is unchanged. Wallet API: `contactChecks` on the single-mint endpoint and in the list only with `include=facts` (the default list is unchanged and a test pins that); `WalletExtra.contactChecks` from the same snapshot query (`m.contact_checks`).
- **Wording (Part N).** `formatValid: false` means "format not recognised by MintRadar", never "invalid", "fake" or "wrong": Mint Detail says `Nostr contact format not recognised` (`contactChecksLine`, with a test and an e2e check banning `invalid` / `not valid`), and `API.md`, the OpenAPI description, `/for-wallets` and `walletFields.ts` say the same. A mint whose contact is in a form we do not know is not reported as having a bad one.
- **Rules version (Part N).** `CONTACT_RULES_VERSION` (now 2) is stored as `rules` on every entry. `scheduleContactChecks` passes `storedRulesCurrent(storedRaw)` to `isCheckDue`; an entry with another or no `rules` makes the check due at the next successful probe of the mint (so within one probe cycle after a deploy, no manual DB write), and the rewritten result carries the current version, so a mint is rechecked once per version, not on every probe. Raise the constant whenever a rule changes what `formatValid` or `domainResolves` can say. Mints that are offline are rechecked when they next answer.
- **Tests.** `contactChecks.test.ts` (syntax, public names, nostr/url/handle, DNS outcomes, cache, concurrency, 3-email cap, no request, canary), `contactChecksProbe.test.ts`, `contactChecks.pg.test.ts` (`MR_PG_TEST_URL`), `integration/wallet-api-w2b.test.ts` (`contactChecks` block), `integration/mint-probe.test.ts`. Run the PG files one at a time (`vitest run --no-file-parallelism`) when `MR_PG_TEST_URL` is set: they share one database and collide in parallel.
