# MintRadar — Third-party requests from the browser (2026-10-04)

Everything the app contacts **from the visitor's browser** other than its own origin (`mintradar.org`). Measured with a scratch Playwright script (e2e mocks, `bypassCSP` because the dev CSP is stricter than production's `connect-src 'self' https: wss:`, every foreign origin answered locally, no live site, no real relays), then cross-checked against the code. Server-side requests (backend → audit.8333.space, GitHub API, mints, relays) are out of scope here. **Server-side, since 2026-10-04:** the backend also contacts `cashu.info` — two GET requests (`/api/v1/mints`, `/api/v1/swaps?limit=500`) every 10 minutes, no personal data, no visitor information; the visitor's browser never contacts it (the Audit tab reads our own `/api/mints/audit-cz`). **Server-side, since 2026-10-06:** the backend also contacts two profile relays, `wss://profiles.nostr1.com` (primary) and `wss://relay.nos.social` (fallback), at the end of each hourly reviews sync run: at most 8 REQs (`kinds:[0], authors:[≤50 review-author / mint-key pubkeys]`), one connection per relay per run. The only data sent is public pubkeys; no visitor request is added and no visitor information is sent (the browser's own profile lookups and relay lists are unchanged; the browser reads the stored names from our own `/api/mints/nostr-reviews`). See `reviews-and-nostr.md`. **Also on demand:** opening the Audit tab of a covered mint can make the backend request `GET /api/v1/mints/{id}` (the id is taken only from a stored `https://cashu.info/mint/…` page URL and validated), cached 10 minutes per mint, one shared fetch for concurrent requests, 5 s timeout, 128 KiB cap; worst case about 65 mints × 6 per hour = 390/h plus the cron's 12/h. No personal data, no visitor information is sent.

Every foreign origin below receives at least the visitor's **IP address and User-Agent**; the "Data" column lists what else.

### Relays that do not come from our own constants (limited 2026-10-06, `src/core/nostr/relayHints.ts`)
- **naddr links** (`/mint/nostr/<naddr>`, `MintNaddr.tsx`): the relay hints inside the link are written by whoever made the link, so a hint is used only if it is a `wss://` relay whose host (and port) is exactly one we already know (`REVIEW_RELAYS`, `REVIEW_READ_RELAYS`, `DISCOVERY_RELAYS`, `PROFILE_RELAYS`), at most 3, deduplicated. Anything else (unknown host, `ws://`, IP literal, localhost) is ignored without a request. The lookup always also asks the default relays of the page (damus, nos.lol, cashumints.space, primal, snort, offchain, wellorder) — before this change a link with hints asked only the hints. A crafted link can therefore no longer make the visitor's browser contact a relay of the link author's choosing.
- **The logged-in user's own NIP-65 list** (`useUserRelays`, watchlist sync fetch/publish, own-profile fallback lookup in `client.ts`): only `wss://` public host names (no IP literals, localhost, `.onion`, `.local`, userinfo), deduplicated, and at most the first 10. Our connections are capped; the user's list itself is never edited. Notification subscriptions send the same filtered read list (≤ 10) to the server, which validates again.
- **bunker:// relay** (pasted by the user) is unchanged and still listed above.

### Not contacting anything third-party (verified)
- Logged-out **Dashboard**, **Stats**, **Wallets**, **Learn**, **NUT explorer**, Token Inspector's *local decode*, **Submit a mint** Single-URL and Bulk (`/api/mint/probe`, `/api/mints/discover` are own origin) — zero foreign requests.
- Mint QR modal — zero requests; the QR is rendered locally (`QRCodeSVG`) since 2026-10-04 (was `api.qrserver.com`, which received the mint URL).
- Reviewer / recommender avatars — no longer loaded since 2026-10-04 (initials tiles). Mint icons go through `/api/mint/icon`. Fonts are self-hosted. No analytics, no CDN scripts.
- nostr.mintradar.org (our own relay) is one of the discovery/publish relays; it is first-party but still a separate origin.

## Best Mint wizard — does it fetch from mints in the browser?
**Yes.** `Tools.tsx` (`BestMintWizard`, the `latencyResults` block, ~line 656): after filtering the known-mints list it takes the top **20** candidates by Reliability Score and does `fetch(`${m.url}/v1/info`, { signal: AbortSignal.timeout(5000) })` for each, in parallel, **on every "Find my mint" click** (no caching between runs). Only the HTTP status and the round-trip time are used.

Everything else the ranking needs already comes from the backend's known-mints API (`/api/mints/known`): `reliabilityScore`, `nutCount`, `units`, `nutsLimits` (NUT-9/11/17), `mintMethods` / `meltMethods` (per-unit limits), `latencyMs` (server-side, measured by the 5-minute probe from Nuremberg) — and the wizard never reads the mint's own `/v1/info` body.

So the same result **could** come from backend data by using `latencyMs` instead of the browser round-trip. The trade-off is semantic: the option is labelled **"Fast from here"**, i.e. it ranks by latency *from the visitor*, while the backend value is latency *from Nuremberg*. Removing the 20 direct requests would also remove an IP/UA disclosure to up to 20 mint operators per run. Not changed in this task; it needs a product decision on the "Fast from here" wording.

## Notes
- Production CSP (`deploy/nginx.conf`) allows `connect-src 'self' https: wss:` and `img-src 'self' https: data:`, so the CSP does not restrict any of the above; the dev server CSP (`vite.config.ts`) blocks `https:` fetches, so the mint/NIP-05 requests only appear in dev/e2e with `bypassCSP`.
- The README claims were deliberately not touched in this task.

## Server-side requests to the audit sources (not the visitor's browser)

The backend (never the browser) contacts `cashu.info` (formerly audit.cashu.cz, same service): the mint feed and the swaps feed every 10 minutes (about 12 requests/h) and the per-mint detail every 30 minutes for each covered tracked mint, one at a time with a 2 s pause (about 130 requests/h). None is triggered by a visitor; `/api/mints/audit-cz` reads the database only. Public technical data about mints; no personal data is requested. The mint host's public DNS A record is resolved by the backend itself (not cashu.info) and shown as the IP row.
